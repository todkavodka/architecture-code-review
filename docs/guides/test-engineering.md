# Test Engineering: подробное руководство

`Test Engineering` отвечает не на вопрос «все ли тесты зелёные», а на более важный вопрос:

> Какие существенные поведения системы действительно доказаны исполняемыми тестами, что подтверждено только частично и где доказательств пока нет?

Это самостоятельное направление `Review Suite`. Для него не нужно обязательно запускать `Architecture Review` или `Code Quality Review`.

## Когда выбирать Test Engineering

Используйте `Test Engineering`, если нужно:

- понять, какие важные поведения системы реально проверены;
- найти случаи, где тесты есть, но не доказывают нужное поведение;
- выявить важные сценарии без исполняемого доказательства;
- сопоставить заявленный контракт, реализацию, потребителей и тесты;
- подготовить `Test Plan`;
- спроектировать тестовую среду;
- подготовить проект имитатора внешнего сервиса;
- подготовить план E2E-проверок;
- сформировать негативные и граничные тестовые случаи для API.

Большое число тестов и высокий процент покрытия не гарантируют достаточность доказательств. Можно иметь тысячи проходящих тестов и при этом не проверять критический путь с тайм-аутом после фиксации транзакции.

## Что получает пользователь

При включении `Test Engineering` обязательно формируется `Test Assurance`.

Он состоит как минимум из двух связанных пользовательских документов:

```text
Test Assurance Summary
Test Assurance Map
```

`Summary` даёт краткий вывод: что подтверждено, что подтверждено частично, чего не хватает.

`Map` показывает, как существенные поведения связаны с целями проверки, тестами и пробелами.

Дополнительно можно выбрать:

```text
Test Plan
Contract Consistency Report
Test Environment Design
Service Simulator Design
Service Simulator Implementation Plan
E2E Test Plan
```

Не выбирайте все документы «на всякий случай». Каждый дополнительный результат нужен только тогда, когда он помогает решать конкретную задачу.

## Как строится анализ

Общая цепочка выглядит так:

```text
исходный код, тесты, схемы и внешние источники
    ↓
WS-* / EV-* — наблюдения и доказательства
    ↓
Shared Technical Model
    ↓
семантика Test Engineering
    ↓
BC-* / CC-* / MAT-* / TM-* / GAP-* / TASK-*
    ↓
человекочитаемые документы
```

`Test Engineering` не создаёт собственную параллельную модель архитектуры. Если для проверки нужен факт об интерфейсе, потоке или хранилище, используется принятая часть Shared Technical Model.

## `BC-*`: существенное поведение

`BC-*` описывает одно независимо проверяемое поведение системы.

Примеры:

```text
BC-021
Повторная попытка после неоднозначного тайм-аута не создаёт второй заказ.

BC-022
Для одного заказа наблюдаемо не более одного окончательного события.
```

`BC-*` — не тестовый случай и не строка требования. Это принятое описание поведения, которое должно быть доказано.

Человекочитаемый `Behavior Contract Model` строится из принятых `BC-*`, но не становится их владельцем.

## `CC-*`: согласованность контракта

Иногда разные представления одного контракта расходятся.

Например:

```text
DECLARED     OpenAPI: повторный id → 409
IMPLEMENTED  сервер: повторный id → 200 с прежним объектом
CONSUMED     клиент ожидает 200
TESTED       тесты проверяют 200
```

Такое расхождение фиксируется как `CC-*`.

Важно: ни одна сторона не считается автоматически правильной. Нужно установить, где находится принятый источник смысла и как должно быть согласовано поведение.

`Contract Consistency Report` — представление этих записей, а не источник истины.

## `MAT-*`: что необходимо доказать

`MAT-*` описывает существенную цель проверки.

Например:

```text
MAT-011
Нужно доказать, что успешная фиксация заказа с потерянным ответом не приводит
к созданию второго заказа при повторной попытке.
```

Существенность здесь означает важность для доказательства поведения, а не тяжесть дефекта.

## `TM-*`: чем поведение доказано

`TM-*` связывает цель проверки с конкретным исполняемым доказательством и его результатом.

Например:

```text
MAT-011
  ↓
TM-031
  test_retry_after_timeout
  verdict: PARTIAL
```

`TM-*` — не исходный код теста и не `Test Plan`. Это запись о том, какое доказательство существует и что именно оно подтверждает.

## `GAP-*`: чего не хватает

`GAP-*` означает, что для существенного поведения нет достаточного доказательства.

Причины могут быть разными:

- теста нет;
- тест покрывает только часть сценария;
- тест проверяет другой режим;
- тест есть, но не исполнялся на нужной ревизии;
- окружение не соответствует требуемому;
- результат нельзя связать с нужным поведением;
- тест создаёт ложное ощущение покрытия.

`GAP-*` не равен автоматически задаче на разработку. Сначала фиксируется недостаток доказательства, затем при необходимости создаётся `TASK-*`.

## `TASK-*`: работа по устранению пробела

`TASK-*` описывает действие: добавить тест, подготовить окружение, получить недостающее доказательство, проверить внешний сервис и т.д.

Ключевое правило:

```text
TASK COMPLETED != GAP RESOLVED
```

То, что инженер написал тест, ещё не доказывает, что пробел устранён. Нужны фактическое исполнение, принятый результат и повторная проверка соответствующего `GAP-*`.

## Сгенерированный тест не означает TESTED

Skill умеет формировать тестовые случаи. Это полезно, но важно не перепутать план и доказательство.

```text
описан тестовый случай
        ≠
тест выполнен
        ≠
поведение доказано
```

Чтобы утверждать `TESTED`, нужны принятые данные фактического исполнения, привязанные к:

- нужной ревизии;
- нужному окружению;
- конкретному результату;
- соответствующему поведению;
- происхождению доказательства.

Текст `expected: 413` в `Test Plan` не доказывает, что сервер действительно вернул `413`.

## Негативные и граничные API-тесты

Для API полезно проверять границы не одним «очень большим значением», а вокруг известного ограничения.

Если лимит равен `N`, типичный набор:

```text
N - 1
N
N + 1
```

Это применимо к:

- длине строк;
- размеру коллекций;
- числовым диапазонам;
- размеру тела запроса;
- размеру загрузки;
- pagination;
- глубине вложенности;
- количеству multipart-частей.

Также важны:

- отсутствующее обязательное поле;
- `null` против отсутствующего значения;
- неизвестное поле;
- неверный `Content-Type`;
- повреждённый JSON;
- неверное enum-значение;
- oversized body;
- oversized upload.

Если точный предел неизвестен, skill не должен придумывать его. В этом случае результатом становится открытый вопрос или требование установить границу.

## Почему ограничение поля не заменяет ограничение запроса

Путь обработки запроса может выглядеть так:

```text
HTTP body
  ↓
чтение в память
  ↓
парсинг JSON
  ↓
валидация схемы
  ↓
проверка maxLength
```

Если `maxLength = 255`, это защищает значение поля, но не обязательно защищает сервер от тела запроса размером в сотни мегабайт, если оно полностью читается до валидации.

Поэтому Test Engineering различает:

- транспортную границу;
- парсинг и материализацию;
- проверку схемы;
- бизнес-валидацию.

## Проверка контрактов

При наличии формализованного внешнего контракта могут сравниваться четыре представления:

```text
DECLARED
IMPLEMENTED
CONSUMED
TESTED
```

Пример:

```text
DECLARED     OpenAPI
IMPLEMENTED  серверный код
CONSUMED     клиентский код
TESTED       фактически выполненные тесты
```

Если они расходятся, skill фиксирует расхождение. Он не выбирает победителя автоматически.

Особенно важно, что `TESTED` нельзя заполнить только на основании сгенерированного тестового случая. Нужны данные исполнения.

## Как читать Test Assurance

Начните с `Test Assurance Summary`.

Для каждого существенного направления полезно видеть:

```text
поведение
  ↓
что нужно доказать
  ↓
какие тесты существуют
  ↓
что они фактически доказали
  ↓
какие пробелы остались
```

После этого `Test Assurance Map` позволяет провалиться до конкретных `BC-*`, `MAT-*`, `TM-*`, `GAP-*` и доказательств.

## Что делать после изменения кода

Не запускайте Test Engineering с нуля после каждого commit.

Если изменение ещё не принято, используйте `CHANGE_REVIEW` и оцените, какие поведения и доказательства оно затрагивает.

Если новый код уже считается текущим состоянием, используйте `REVALIDATE`.

Пример:

```text
изменился retry-механизм
    ↓
затронут BC-021
    ↓
затронут MAT-011
    ↓
старый TM-031 может стать STALE
    ↓
нужны новые execution evidence
    ↓
GAP-008 повторно оценивается
```

Наличие нового тестового файла не означает автоматическое закрытие `GAP-*`.

Подробно: [Что делать после изменения кода](after-code-changes.md).

## Когда использовать EXTEND

`EXTEND` нужен, если пакет уже существует, но требуется добавить новый результат или новую допустимую область.

Например:

```text
раньше: Test Assurance
теперь дополнительно нужен: Test Environment Design
```

Это не повод заново выполнять весь аудит.

## Частые ошибки

Не следует:

- считать количество тестов показателем достаточности;
- считать coverage доказательством поведения;
- считать `Test Plan` выполненным тестированием;
- считать написанный тест закрытым `GAP-*`;
- смешивать `GAP-*` и архитектурные `RF-*`;
- превращать `TASK-*` в источник истины о тестовом покрытии;
- придумывать неизвестные граничные значения;
- считать OpenAPI-схему доказательством фактической серверной валидации;
- повторно запускать весь модуль после каждого изменения.
