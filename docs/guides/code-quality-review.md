# Руководство по Code Quality Review

`Code Quality Review` ищет не стилистические отличия сами по себе, а
конкретные механизмы реализации с доказуемым существенным инженерным
последствием. Это самостоятельный модуль `Review Suite`: его можно выбрать в
`Requested Work` без включения `Architecture Review` или `Test Engineering`.
Для `NEW` также допустим самостоятельный output/view-запрос, если он разрешён
маршрутизацией; внутренние зависимости такого запроса не считаются выбранными
пользователем модулями.

## Когда выбирать

Выбирайте `Code Quality Review`, когда нужно исследовать механизмы реализации,
которые могут заметно увеличить стоимость изменений, риск дефектов,
эксплуатационную хрупкость, сложность локализации, ненадёжность работы с
зависимостями или трудность проверки кода. Например, это может быть
дублирование с расходящимся поведением, чрезмерная сложность с подтверждённым
риском изменений, ошибки управления ресурсами и жизненным циклом, небезопасное
конкурентное выполнение, хрупкая обработка ошибок либо неверное использование
фреймворка.

Размер файла, предупреждение анализатора, метрика или эвристика сами по себе
не создают замечание. Они могут дать наблюдение или кандидата на замечание, но
не заменяют доказательство существенного последствия.

## От фактов к замечаниям

Модуль использует общий фактический слой и не строит собственную конкурирующую
модель системы:

```text
источник
→ доказательства и записи WS-*/EV-*
→ Shared Technical Model
→ анализ качества кода
→ кандидат на замечание
→ принятое CQ-*
→ CQRA-* при необходимости
→ человекочитаемые проекции
```

Когда для интерпретации нужен факт о границе системы, интерфейсе, потоке или
конфигурации, используется принятый достаточный срез `Shared Technical Model`
(STM). Недостающие, спорные или устаревшие факты возвращаются в общий слой
доказательств и STM; `Code Quality Review` не переписывает STM и не замещает
его собственными выводами. Подробнее эта граница объяснена в
[разделе о доказательствах и STM](../concepts/evidence-and-technical-model.md).

Кандидат — временная предварительная оценка, а не источник истины. Для
принятия `CQ-*` нужна цепочка «наблюдение → интерпретация механизма →
доказанное существенное последствие». Информационное наблюдение, даже если оно
получено инструментом, не становится `CQ-*` автоматически.

## `CQ-*`: замечания по качеству кода

`CQ-*` — устойчивый идентификатор принятого замечания, которым владеет `Code
Quality Review`. Он не равен архитектурному выводу `RF-*`, записи `GAP-*`,
`TASK-*` или иной семантике `Test Engineering`; общие доказательства или связь
между записями не передают владение.

Принятое замечание фиксирует конкретный механизм реализации, область, прямые
доказательства и происхождение вывода, существенное последствие, а также его
применимость, серьёзность и достоверность интерпретации. Существенность — это
не «код выглядит плохо» и не личное предпочтение. Она связывает механизм с
подтверждённым последствием, например с риском дефекта, ценой сопровождения,
хрупкостью эксплуатации, небезопасной связностью или риском локализационной
ошибки.

Серьёзность и достоверность — независимые характеристики. Серьёзность
`CRITICAL`, `HIGH`, `MEDIUM` или `LOW` описывает масштаб и срочность
последствия. Достоверность показывает, насколько надёжны наблюдение и его
интерпретация. Высокая серьёзность не означает автоматически высокую
достоверность и наоборот.

У принятого замечания жизненный цикл ограничен переходами:

```text
ACTIVE → RESOLVED
ACTIVE → SUPERSEDED
```

`RESOLVED` требует доказанной повторной проверки того, что проблема более не
существует. `SUPERSEDED` требует нового существенно отличающегося источника
истины или явного решения о замещении. Другие формальные заменяющие состояния
для этого жизненного цикла не вводятся.

Применимость и решение о дальнейшей судьбе замечания — отдельные оси.
`APPLICABLE`, `NOT_APPLICABLE` и `EXCLUDED` определяют применимость правила или
области; `NOT_APPLICABLE` не означает `FALSE_POSITIVE`. `FALSE_POSITIVE`
отклоняет неверную интерпретацию кандидата, `ACCEPTED_EXCEPTION` фиксирует
реальную проблему, сознательно принятую по исключению, а `WONT_FIX` — реальную
проблему, для которой устранение пока не планируется. Ни `ACCEPTED_EXCEPTION`,
ни `WONT_FIX` не равны `RESOLVED` и не являются состояниями жизненного цикла.
`EXCLUDED` означает решение об исключении области, а не доказанное отсутствие
риска качества кода.

Состояние охвата `COMPLETE`, `PARTIAL` или `BLOCKED` описывает, насколько
исследована выбранная область. Оно не является жизненным циклом `CQ-*`:
`COMPLETE` не означает отсутствия замечаний, а `PARTIAL` не отменяет уже
принятые замечания с достаточными доказательствами.

Связи `DUPLICATE`, `CORRELATED`, `CAUSAL`, `ESCALATED`, `DERIVED` и
`INDEPENDENT` также не являются статусами или решениями по замечанию. Они
поясняют связь отдельных записей, не перенося между ними серьёзность, жизненный
цикл или владение. В частности, `DUPLICATE` не означает неявного удаления
записи.

## Проверка устойчивости API к входным данным

`Code Quality Review` может рассматривать API input robustness как аспект
качества реализации. Факты об интерфейсе, его схеме и конфигурации остаются в
общем фактическом слое и Stage F; `Code Quality Review` не создаёт второй
каталог API. Его задача — определить, есть ли в реализации доказуемый
существенный механизм риска или недоказанная граница.

Главное разделение — два независимых уровня ограничений:

```text
запрос
→ transport/container limit
→ parsing / materialization
→ schema/field validation
→ business processing
```

Транспортный лимит ограничивает то, сколько данных сервер, gateway, framework
или parser допустит до дальнейшей обработки. Ограничение поля определяет,
какое значение допустимо уже внутри разобранного запроса. Одно не заменяет
другое.

Например, схема может содержать:

```text
name: string
maxLength: 255
```

но если приложение сначала целиком читает JSON body в память, а только потом
проверяет `maxLength`, этот `maxLength` не доказывает защиту от очень большого
запроса. Для сценария со строкой порядка 2 ГБ инструмент должен отдельно
установить, есть ли лимит тела запроса и где именно он применяется.

При этом отсутствие доказательства лимита не равно автоматически подтверждённой
уязвимости. Корректный вывод может выглядеть так:

```text
field constraint: EVIDENCED
transport boundary: UNRESOLVED
resource-exhaustion protection: NOT ESTABLISHED
```

Для API могут рассматриваться, среди прочего:

- лимит тела запроса;
- длина строк;
- размер коллекций;
- числовые диапазоны;
- глубина вложенности;
- размер и количество uploads/multipart parts;
- ограничения headers/query/cookies;
- `Content-Type` и malformed payload;
- политика неизвестных полей;
- реальное применение схемы;
- порядок materialization и validation;
- ресурсоёмкость parser/deserializer;
- expansion после decompression;
- ограничения pagination.

Типовые классы замечаний включают `MISSING_REQUEST_SIZE_LIMIT`,
`UNBOUNDED_STRING`, `UNBOUNDED_COLLECTION`, `UNBOUNDED_UPLOAD`,
`SCHEMA_NOT_ENFORCED`, `VALIDATION_AFTER_MATERIALIZATION`,
`UNEXPECTED_FIELD_ACCEPTANCE`, `PARSER_RESOURCE_EXHAUSTION`,
`UNBOUNDED_PAGINATION`, `UNBOUNDED_NUMERIC_INPUT`, `UNBOUNDED_NESTING`,
`UNBOUNDED_MULTIPART` и `COMPRESSION_EXPANSION_RISK`.

Эти классы не задают универсальные бизнес-лимиты. Отсутствие `maxLength` не
означает автоматически `HIGH`, а число вроде 255 нельзя придумывать как
универсально правильное. Ожидаемая граница должна опираться на контракт,
политику, ресурсный бюджет или другое принятое доказательство.

Особенно осторожно интерпретируются источники доказательств:

- `maxlength` только в UI — слабая подсказка, а не server-side enforcement;
- OpenAPI `maxLength` — декларация схемы, а не доказательство применения валидатора;
- framework default требует доказательства применимости к фактическому deployed path;
- reverse proxy limit защищает только подтверждённый путь трафика;
- streaming и buffered processing рассматриваются отдельно.

## `CQRA-*`: действия по устранению

`CQRA-*` — отдельные записи действий по устранению проблем, которыми также
владеет `Code Quality Review`. Одно замечание может иметь несколько действий,
а одно действие — относиться к нескольким замечаниям. `CQRA-*` не является
`CQ-*` и не заменяет `TASK-*`, принадлежащие `Test Engineering`.

Жизненный цикл действия использует `PROPOSED`, `PLANNED`, `COMPLETED`,
`CANCELLED` и `SUPERSEDED` в допустимых контрактом переходах. Когда действие
достигло `COMPLETED`, это подтверждает выполнение работы, но не закрывает
связанное замечание автоматически:

```text
CQRA COMPLETED != CQ RESOLVED
```

Для каждого связанного `CQ-*` нужны новые адресные доказательства и отдельная
повторная проверка. Только она может сохранить замечание активным, перевести
его в `RESOLVED`, показать необходимость `SUPERSEDED` или обозначить отсутствие
необходимых доказательств как `BLOCKED`.

## Границы с другими модулями

`Code Quality Review` отвечает на вопрос «что в реализации сделано плохо и
почему это существенно». `Architecture Review` отвечает на вопрос «что это
значит для архитектуры». Одна причина может породить связанные `CQ-*` и `RF-*`,
но один идентификатор не заменяет другой и каждый модуль принимает собственное
решение.

Недостаток тестового доказательства поведения относится к `GAP-*`, а не к
`CQ-*`. В то же время механизм реализации, который существенно ухудшает
проверяемость, может быть самостоятельным замечанием по качеству кода. Это не
создаёт `BC-*`, `CC-*`, `MAT-*`, `TM-*`, `GAP-*` или `TASK-*` простым
переименованием `CQ-*`.

Для API это разделение означает: Stage F фиксирует, что известно об интерфейсе
и его границах; Code Quality оценивает качество реализации; Test Engineering
описывает, что нужно доказать граничными и негативными тестами. Сгенерированный
тестовый случай не превращается в `CQ-*` и не доказывает устранение замечания.

## Выбираемые итоговые документы

Все следующие документы — явно выбираемые производные проекции принятого
семантического состояния; включение модуля не делает ни один из них
обязательным автоматически:

```text
Code Quality Findings View
Code Quality Summary
Maintainability Hotspots
Code Quality Roadmap Contribution
```

`Code Quality Findings View` помогает работать с принятыми `CQ-*`; `Code
Quality Summary` кратко показывает наиболее существенные выводы и ограничения
охвата; `Maintainability Hotspots` группирует принятые замечания по областям
системы; `Code Quality Roadmap Contribution` представляет связанные действия и
зависимости для планирования.

Эти документы выводятся из принятого семантического состояния и доказательств.
Они не создают, не изменяют, не разрешают и не заменяют `CQ-*` или `CQRA-*`.
В частности, `Code Quality Roadmap Contribution` не является записью действия
`CQRA-*`, а `Maintainability Hotspots` не владеет идентичностью или жизненным
циклом замечания. О правилах проекций и пакетов читайте в
[соответствующем разделе](../concepts/projections-and-packages.md).

## Повторное использование и изменения

Если изменились исходный код, конфигурация, зависимость, доказательство или
связанный факт STM, используйте `REVALIDATE`. Он определяет затронутые записи
и получает только необходимые новые доказательства; несвязанные принятые
замечания сохраняются, если их зависимости остаются действительными.
`REVALIDATE` не равен пересборке документов и не запускает полный аудит без
доказанного влияния.

Чтобы добавить область или итоговый документ позднее, используйте `EXTEND`.
Он аддитивен: принятый прежний выбор сохраняется, а пользователю предлагаются
только допустимые добавления. `RESUME` продолжает незавершённую работу, а
`USE_EXISTING` использует принятое актуальное состояние. Практические правила
повторной проверки приведены в [справочнике процессов](../reference/workflows.md),
а различие между актуальностью семантики и документов — в
[разделе о жизненном цикле и актуальности](../concepts/lifecycle-and-freshness.md).
