# Code Quality Review: подробное руководство

`Code Quality Review` проверяет качество реализации не по вкусовым предпочтениям и не по числу предупреждений анализатора, а по **конкретным механизмам кода, которые создают существенное инженерное последствие**.

Это самостоятельное направление `Review Suite`. Его можно использовать отдельно от `Architecture Review` и `Test Engineering`.

## Когда выбирать Code Quality Review

Используйте его, если нужно найти проблемы, которые заметно влияют на:

- стоимость изменений;
- риск дефектов;
- надёжность;
- тестируемость;
- конкурентность;
- управление ресурсами;
- жизненный цикл объектов и процессов;
- локализацию;
- работу с зависимостями;
- обработку ошибок;
- устойчивость API к входным данным;
- сопровождаемость крупных или сложных областей кода.

Хороший кандидат на `CQ-*` отвечает на три вопроса:

```text
что именно сделано
    ↓
какое существенное последствие это создаёт
    ↓
чем это доказано
```

Если нет существенного последствия, размер файла, сложность функции или предупреждение линтера сами по себе не являются finding.

## Как строится анализ

Общая цепочка:

```text
исходный код и другие источники
    ↓
WS-* / EV-* — наблюдения
    ↓
Shared Technical Model, когда нужен фактический контекст
    ↓
кандидат на Code Quality finding
    ↓
независимая проверка и принятие
    ↓
CQ-*
    ↓
CQRA-* при необходимости
    ↓
человекочитаемые документы
```

`Code Quality Review` не создаёт вторую архитектурную модель системы. Если для вывода нужен факт об интерфейсе, потоке, компоненте или конфигурации, используется принятая часть Shared Technical Model.

## Что считается Code Quality finding

`CQ-*` — принятая семантическая запись о конкретной проблеме реализации.

Она должна содержать как минимум:

- конкретный механизм;
- область, где он проявляется;
- доказательства;
- существенное последствие;
- серьёзность;
- применимость;
- происхождение;
- актуальность относительно источника.

Пример:

```text
CQ-014
механизм:
  три независимые реализации выбора резервного языка

последствие:
  один и тот же профиль пользователя получает разный язык интерфейса
  в разных точках входа

severity:
  MEDIUM
```

Это сильнее формулировки «дублирование кода». Дублирование само по себе — наблюдение. Finding появляется, когда доказано существенное последствие.

## Что не является finding автоматически

Само по себе недостаточно:

- большой файл;
- длинная функция;
- высокий cyclomatic complexity;
- предупреждение статического анализатора;
- дублированный блок;
- отсутствие комментария;
- нестандартный стиль;
- устаревшая библиотека;
- необычный шаблон кода.

Каждый из этих сигналов может стать входом в исследование, но не заменяет доказательство.

## Жизненный цикл CQ

Принятый `CQ-*` использует минимальный жизненный цикл:

```text
ACTIVE → RESOLVED
ACTIVE → SUPERSEDED
```

`RESOLVED` требует свежих доказательств того, что механизм и его существенное последствие больше не существуют в проверенном состоянии.

`SUPERSEDED` означает, что прежняя запись заменена другим принятым представлением проблемы. Это не доказательство исправления.

Если та же проблема возвращается после разрешения, создаётся новая `ACTIVE`-редакция той же идентичности; сравнение baseline показывает `REOPENED`.

## Серьёзность и достоверность — разные вещи

Серьёзность отвечает на вопрос:

> Насколько существенно последствие?

Достоверность отвечает на вопрос:

> Насколько хорошо доказаны наблюдение и интерпретация?

Поэтому возможны разные сочетания:

```text
HIGH severity + MEDIUM confidence
MEDIUM severity + HIGH confidence
```

Нельзя автоматически повышать серьёзность только потому, что доказательства очень убедительны.

## Применимость, disposition и lifecycle нельзя смешивать

Это разные оси.

Применимость может описывать, относится ли правило или область к выбранному коду.

Disposition может показывать решение команды о дальнейшей судьбе реальной проблемы.

Lifecycle показывает, существует ли сама проблема в принятом техническом смысле.

Например:

```text
ACTIVE + ACCEPTED_EXCEPTION
```

означает реальную текущую проблему, которую команда осознанно приняла как исключение.

Это не `RESOLVED`.

Аналогично:

```text
ACTIVE + WONT_FIX
```

остаётся активным finding. Отказ от исправления не доказывает исчезновение проблемы.

## Accepted risk и WONT_FIX

Не следует считать любой `WONT_FIX` автоматически принятым риском.

Принятый риск требует явного решения владельца/управления, области, основания и происхождения решения.

`WONT_FIX` может означать только то, что устранение не планируется. Это всё ещё реальная текущая проблема.

## `CQRA-*`: действия по устранению

`CQRA-*` — запись о работе по устранению одного или нескольких `CQ-*`.

Пример:

```text
CQRA-006
relates_to: CQ-014
action:
  вынести выбор резервного языка в единый механизм
status:
  PLANNED
```

Ключевое правило:

```text
CQRA COMPLETED != CQ RESOLVED
```

Даже если код изменён и remediation завершена, finding закрывается только после отдельной повторной проверки.

Это защищает от очень распространённой ошибки:

```text
задача в Jira закрыта
        ↓
значит проблема исправлена
```

Такой вывод без доказательств недопустим.

## API и устойчивость к входным данным

`Code Quality Review` может исследовать, насколько реализация API защищена от неконтролируемого входа.

Особенно важно различать этапы:

```text
transport/container limit
    ↓
чтение и материализация запроса
    ↓
парсинг
    ↓
валидация схемы
    ↓
бизнес-обработка
```

### Пример: maxLength не равен body limit

Допустим, схема содержит:

```text
name: string
maxLength: 255
```

Это доказывает только заявленное ограничение поля, если схема действительно применяется.

Но сервер может сначала сделать:

```text
прочитать всё тело запроса в память
    ↓
разобрать JSON
    ↓
проверить maxLength
```

В таком случае `maxLength` не доказывает защиту от гигантского тела запроса.

Нужно отдельно проверить:

- есть ли ограничение размера body;
- где оно применяется;
- происходит ли проверка до материализации;
- действует ли оно на фактическом пути трафика;
- не снимается ли ограничение между proxy и приложением.

## Какие границы API полезно проверять

В зависимости от области:

- размер HTTP body;
- размер upload;
- длина строк;
- количество элементов коллекции;
- числовые диапазоны;
- глубина вложенности;
- количество multipart-частей;
- headers, query и cookies;
- pagination;
- неизвестные поля;
- malformed payload;
- неверный `Content-Type`;
- decompression expansion;
- поведение parser/deserializer.

Если точный лимит неизвестен, finding должен отражать неизвестность, а не выдумывать универсальное число.

Корректная формулировка может быть такой:

```text
ограничение поля: подтверждено
ограничение тела запроса: не установлено
защита от resource exhaustion: не доказана
```

а не:

```text
сервер точно уязвим
```

если доказательств для такого вывода нет.

## Как читать результаты

В зависимости от выбранной конфигурации можно получить:

```text
Code Quality Findings View
Code Quality Summary
Maintainability Hotspots
Code Quality Roadmap Contribution
```

Все эти документы — представления принятых `CQ-*` и связанных данных.

Они не являются источником истины. Если нужно изменить finding, исправляется владеющая семантическая запись, а затем при необходимости пересобирается проекция.

## Maintainability Hotspots

`Maintainability Hotspots` должен показывать области, где несколько подтверждённых проблем создают связанную нагрузку сопровождения.

Это не рейтинг файлов по размеру.

Например, каталог можно считать hotspot, если в нём одновременно обнаружены:

- дублирование поведения;
- нестабильные зависимости;
- сложный жизненный цикл ресурсов;
- высокая связность;
- ошибки обработки состояния;
- плохая тестируемость.

Но один файл на 3000 строк без доказанного последствия не обязан становиться hotspot.

## Граница с Architecture Review

`Code Quality Review` отвечает:

> Какой механизм реализации создаёт существенную проблему качества?

`Architecture Review` отвечает:

> Что этот механизм означает для архитектуры системы?

Один и тот же участок кода может поддерживать и `CQ-*`, и `RF-*`, но это разные семантические записи с разными владельцами.

Нельзя автоматически превращать `CQ-*` в `RF-*` или наоборот.

## Граница с Test Engineering

Если проблема состоит в отсутствии доказательства поведения, это обычно `GAP-*`.

Если же сама реализация делает поведение трудно проверяемым, это может быть отдельный `CQ-*`.

Пример:

```text
нет теста на timeout path
    → GAP-*

код жёстко связывает network client с глобальным singleton и делает
контролируемый timeout практически непроверяемым
    → возможно CQ-*
```

Обе записи могут быть связаны, но не заменяют друг друга.

## Что делать после изменения кода

Если изменение ещё находится в candidate-ветке или PR, используйте `CHANGE_REVIEW`.

Если новый код уже принят как текущее состояние, используйте `REVALIDATE`.

Пример:

```text
CQ-014 ACTIVE
    ↓
внесена remediation
    ↓
CQRA-006 COMPLETED
    ↓
CQ-014 требует повторной проверки
    ↓
новые доказательства
    ↓
ACTIVE / RESOLVED / SUPERSEDED / BLOCKED
```

Не закрывайте finding только на основании commit message или выполненной задачи.

Подробно: [Что делать после изменения кода](after-code-changes.md).

## Текущие и исторические findings

Закрытые `CQ-*` не удаляются. Они остаются в истории, но не должны раздувать показатель текущего риска.

Отдельно показываются:

```text
зарегистрированные когда-либо
текущие ACTIVE
исторически RESOLVED
исторически SUPERSEDED
принятый остаточный риск
новые / закрытые / reopened между baseline
```

Поэтому рост общего исторического числа findings не обязательно означает ухудшение качества.

## Частые ошибки

Не следует:

- считать style issue полноценным `CQ-*` без существенного последствия;
- считать предупреждение анализатора доказательством;
- закрывать finding по commit message;
- закрывать finding после `CQRA COMPLETED` без revalidation;
- считать `WONT_FIX` равным `RESOLVED`;
- считать accepted risk равным `RESOLVED`;
- смешивать CQ и Architecture authority;
- смешивать CQ и Test Engineering gaps;
- считать OpenAPI limit доказательством фактического enforcement;
- запускать полный Code Quality Review после каждого изменения.
