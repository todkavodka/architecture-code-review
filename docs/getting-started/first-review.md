# Первый полный запуск

Этот пример показывает не только конфигурацию, но и полный жизненный цикл
нового пакета результатов.

## Исходная задача

Предположим, команда получила устаревшую серверную систему и хочет понять:

- как система реально устроена;
- где находятся архитектурные риски;
- насколько текущие тесты подтверждают критические поведения;
- какие механизмы реализации создают существенные проблемы сопровождения.

Запрос к агенту может быть простым:

```text
Используй architecture-code-review для этого репозитория.
Нужен полный инженерный аудит перед модернизацией.
```

## Шаг 1. Определение исходного состояния

Инструмент сначала определяет:

```text
repository identity
previous audit packages
baseline
working-tree state
Project Profile
Session Intent
```

Точные поля выше сохраняются в технических контрактах, но для пользователя это
означает следующее: определить проект, найти предыдущие результаты,
зафиксировать базовую ревизию, учесть незакоммиченные изменения и выбрать
правильный сценарий продолжения работы.

Если пригодного предыдущего аудита нет, будет рекомендован `NEW`.

Если рабочее дерево содержит незакоммиченные изменения, агент должен явно
определить, анализируется ли только зафиксированный `HEAD`, отдельный временный
снимок `EPHEMERAL` или работа останавливается. Это важно для воспроизводимости
доказательств.

## Шаг 2. Review Suite

Для широкого первого аудита команда может выбрать:

```text
Architecture Review: ON
  Depth: STANDARD_FULL
  Endpoint: REVIEW_PLUS_TARGET_AND_ROADMAP

Test Engineering: ON
  Test Assurance
  Test Plan
  Contract Consistency Report

Code Quality Review: ON
  Findings View/Report
  Code Quality Summary
  Maintainability Hotspots
```

Это пример, а не обязательная конфигурация. Инструмент должен помогать
ограничивать область проверки и не включать документы «на всякий случай».

## Шаг 3. Сохранение базового состояния

До основной работы создаются состояние координатора и начальная версия общей
технической модели (`Shared Technical Model`). Это не значит, что вся система
сразу описывается полностью.

Принцип:

```text
создать устойчивую модель для выбранной ревизии
!=
сразу полностью описать весь репозиторий
```

Полный Architecture Review требует принятой фактической модели достаточной ширины до тематического анализа. Более узкий модуль проверки может работать на ограниченной принятой части модели.

## Шаг 4. Доказательства

Исследование разбивается на рабочие области `WS-*`. Внутри них появляются
наблюдения `EV-*`, привязанные к базовой ревизии и точному источнику.

Например:

```text
WS-007-order-publication
  scope: транзакция + публикация события
  baseline: <коммит>

  EV-001
    source: src/orders/service.py
    symbol: complete_order
    observed: фиксация в базе данных происходит до публикации события
```

`EV-*` ещё не является выводом. Эта запись только фиксирует подтверждённое
наблюдение. Понятия рабочей области, наблюдения и вывода определены в
[глоссарии](../reference/glossary.md).

## Шаг 5. Общая техническая модель (STM)

Из достаточных доказательств принимаются технические факты STM:

```text
COMP-API
INT-ORDER-COMPLETE
DS-POSTGRES
EVENT-ORDER-COMPLETED
```

Они связываются с `WS#EV` и друг с другом. Только проверка технической модели
(`Technical Model Gate`) может принять, пересмотреть, отклонить или заменить
новой ревизией факт STM.

## Шаг 6. Анализ выбранными модулями

Дальше каждый модуль интерпретирует общие факты в своей области.

Architecture Review может создать `RF-*` для подтверждённой архитектурной корневой проблемы.

Test Engineering может создать:

```text
BC-*
MAT-*
TM-*
GAP-*
```

Code Quality Review может создать `CQ-*`, если конкретный механизм реализации имеет доказанное существенное последствие.

Один и тот же факт может участвовать во всех трёх анализах, но записи не превращаются друг в друга.

## Шаг 7. Проверки перед принятием

Перед публикацией выводов инструмент проверяет достаточность охвата, проводит
независимую проверку кандидатов там, где её требует соответствующий модуль, и
проверяет согласованность зависимых итоговых документов.

Недостаток доказательств должен ограничить ширину вывода, а не маскироваться уверенной формулировкой.

## Шаг 8. Итоговый пакет

Конкретное расположение файлов зависит от соглашений репозитория и выбранных документов. Концептуально пользователь получает:

```text
Architecture Review / реестр выводов
при необходимости: Target Architecture
при необходимости: Remediation Roadmap

Test Assurance: краткое резюме и карта
при необходимости: Test Plan / Contract Consistency Report /
  Test Environment Design / Service Simulator Design / E2E Test Plan

Code Quality Review: выводы / краткое резюме / проблемные зоны

working/
  INDEX.md
  evidence/
  technical-model/
  projections/
  состояние модулей проверки
```

## Шаг 9. Как читать результат

Руководителю или архитектору обычно достаточно начать с основного отчёта,
краткого резюме и дорожной карты.

Инженер, который проверяет конкретный вывод, идёт глубже:

```text
отчёт
  -> RF/CQ/GAP/другая семантическая запись
  -> факт STM / WS#EV
  -> исходный источник
```

Так можно доказать происхождение вывода без повторного анализа всей системы.

## Шаг 10. Что происходит через месяц

Допустим, после аудита появилось 20 новых коммитов.

Не нужно запускать `NEW` только потому, что изменился HEAD. Для принятого пакета используется `REVALIDATE`:

```text
предыдущая базовая ревизия
  -> текущая базовая ревизия
  -> перечень изменений
  -> анализ влияния
  -> минимальная затронутая область зависимостей
  -> новые доказательства
  -> повторная проверка
  -> учёт влияния на итоговые документы
```

Не затронутое изменениями принятое состояние сохраняется.

Подробные правила повторной проверки, актуальности и пересборки документов
приведены в [справочнике процессов](../reference/workflows.md) и разделе
[о жизненном цикле и актуальности](../concepts/lifecycle-and-freshness.md).
