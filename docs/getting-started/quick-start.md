# Быстрый старт

Этот раздел показывает минимальный путь от запроса к первому полезному
результату без необходимости заранее разбираться во внутренних идентификаторах
инструмента.

## 1. Откройте репозиторий

Запустите агента в корне проекта, который нужно проверить.

## 2. Попросите использовать инструмент

Минимальный запрос:

```text
Используй architecture-code-review для этого проекта.
```

Инструмент сначала определит репозиторий, базовую ревизию, существующие пакеты
аудита и рекомендуемый сценарий работы (`Session Intent`). Новый полный аудит
не должен запускаться автоматически, если уже существует пригодное сохранённое
состояние.

## 3. Выберите, что нужно проверить или получить

Для `NEW` показывается Review Suite:

```text
Review Suite

[ ] Architecture Review
[ ] Test Engineering
[ ] Code Quality Review
```

Это три семантических модуля проверки, но запрос не обязан включать хотя бы
один из них. Для начала содержательной работы должен быть непустой `Requested
Work`: выбранный модуль, допустимый самостоятельный итоговый документ/вид или
их сочетание.

```text
capability-only          VALID
standalone-output-only   VALID
mixed                    VALID

нет модулей и нет результатов   INVALID
только Product context          INVALID
```

Внутренние зависимости, которые инструмент разрешает для выполнения запроса,
относятся к `Resolved Work` и не считаются выбранными пользователем модулями.

### Architecture Review

Если нужна архитектурная диагностика, отдельно выберите глубину и конечный результат:

```text
Depth:
  STANDARD_FULL
  FORENSIC

Endpoint:
  REVIEW_ONLY
  REVIEW_PLUS_TARGET_ARCHITECTURE
  REVIEW_PLUS_TARGET_AND_ROADMAP
```

`STANDARD_FULL` подходит для большинства полных аудитов. `FORENSIC` нужен, когда особенно важны спорные границы, конкурентность, чувствительные к безопасности пути выполнения, сложный жизненный цикл и подробная история доказательств.

После включения модуля открывается его конфигурация. Для Architecture Review
нужно явно подтвердить Depth и Endpoint. Для Test Engineering показывается
обязательный Test Assurance и каждый дополнительный результат; для Code
Quality Review показываются все четыре независимых проекции. Непросмотренный
пункт остаётся UNSPECIFIED, а не превращается в NOT_SELECTED. Перед началом
содержательной работы подтверждается единое резюме выбранной конфигурации.

### Test Engineering

`Test Assurance` обязателен при включённом Test Engineering. Остальные документы выбираются по задаче:

```text
Test Assurance                         required
Test Plan                              optional
Contract Consistency Report            optional
Test Environment Design                optional
Service Simulator Design               optional
Service Simulator Implementation Plan  optional
E2E Test Plan                          optional
```

Для API Test Engineering также может подготовить негативные и граничные случаи:
значение сразу ниже/на/выше известной границы, oversized body/upload, неверный
`Content-Type`, malformed payload, слишком глубокую вложенность и другие
проверки. Если точная граница неизвестна, инструмент не придумывает число, а
фиксирует необходимость установить эту границу.

### Сравнить ветку или commit с принятым baseline

Для такой задачи явно укажите `CHANGE_REVIEW` и два источника:

```text
Сравни принятый baseline с branch feature/payments.
Покажи только кандидатные изменения и влияние на существующие находки.
```

Для PR укажите его как кандидат: «Сравни принятый baseline с pull request
`#123`».

Кандидатный результат не меняет принятые факты, тесты, совместимость или
проекции. Если review завершён и данные пригодны для повторного использования,
`RECONCILE_CHANGE` можно подтвердить отдельно; это не запускается само.
`RESUME` доступен только при совпадающем baseline. При несовпадении он
останавливается и предлагает `CHANGE_REVIEW`, `REVALIDATE` и при выполненных
условиях контекстный `RECONCILE_CHANGE`; `EXTEND` и текущий
`PROJECTION_REPAIR` блокируются. Генерация обновлённых проекций после принятого
изменения остаётся отдельным явным действием.

Сгенерированный или принятый тестовый случай не означает `TESTED`. `TESTED`
требует принятых доказательств фактического исполнения для нужной ревизии и
окружения.

После конфигурации модулей NEW всегда показывает отдельный раздел Standalone
Outputs / Technical Documentation. Выберите применимые Provided Interfaces,
Consumed Interfaces, Integrations, Auth and Trust, Failure Behavior и другие
зарегистрированные представления или явно подтвердите NONE. API Report
предлагает ограниченный набор этих существующих разделов для подтверждения; это не
новый модуль и не новая проекция.

### Code Quality Review

Выберите только те человекочитаемые документы, которые действительно нужны:

```text
Findings View/Report
Code Quality Summary
Maintainability Hotspots
Roadmap Contribution
```

Выбор документа не создаёт `CQ-*` автоматически. `CQ-*` появляется только после того, как конкретный механизм реализации подтверждён доказательствами и для него установлено существенное последствие.

При анализе API Code Quality Review отдельно смотрит на транспортные и
прикладные границы входа: размер тела запроса, строки и коллекции, загрузки,
multipart, pagination, порядок парсинга и валидации, применение схемы и другие
ограничения ресурсов. Например, `maxLength` у JSON-поля не заменяет лимит тела
запроса, если приложение сначала целиком материализует большой payload.

## 4. Дайте инструменту провести исследование

Во время анализа инструмент создаёт или переиспользует:

- доказательства, привязанные к базовой ревизии;
- общую техническую модель (`Shared Technical Model`);
- записи выбранных модулей проверки;
- состояние процесса в `working/INDEX.md`;
- выбранные итоговые документы.

Не нужно вручную просить создать `WS-*`, `EV-*` или STM. Это внутренние
механизмы трассировки и повторного использования результатов.

## 5. Читайте результат с верхнего уровня

Для первого чтения используйте основной отчёт или краткое резюме выбранного
модуля. К семантическим записям и доказательствам переходите только тогда,
когда нужно проверить происхождение конкретного вывода.

Типичный путь проверки:

```text
основной отчёт / краткое резюме
  -> вывод или другая семантическая запись
  -> STM / ссылка на доказательство
  -> исходный код или внешний источник
```

Термины «семантическая запись», «вывод» и «доказательство» подробно объяснены
в [глоссарии](../reference/glossary.md); точные идентификаторы в нормативных
контрактах сохраняются без переименования.

## 6. Не запускайте всё заново после каждого изменения

Если аудит уже принят:

- проект изменился → `REVALIDATE`;
- нужен новый итоговый документ или модуль проверки → `EXTEND`;
- нужно продолжить незавершённую работу на совпадающем baseline → `RESUME`;
- нужен уже принятый результат → `USE_EXISTING`;
- сломано только оформление, Markdown, Mermaid или формулировки → `PROJECTION_REPAIR`.

Полные правила сценариев работы приведены в [справочнике
процессов](../reference/workflows.md), а практические шаги — в руководстве
[«Повторное использование и изменения»](../guides/reuse-and-change.md).

## Три минимальных примера

### Только архитектурный аудит

```text
Используй architecture-code-review.
Нужен новый Architecture Review: STANDARD_FULL, REVIEW_ONLY.
Test Engineering и Code Quality Review не включай.
```

### Только качество тестов

```text
Используй architecture-code-review.
Нужен Test Engineering: Test Assurance + Test Plan.
Architecture Review и Code Quality Review не включай.
```

### Только качество реализации

```text
Используй architecture-code-review.
Нужен Code Quality Review: Findings View + Summary.
Architecture Review и Test Engineering не включай.
```
