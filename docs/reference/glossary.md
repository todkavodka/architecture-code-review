# Глоссарий

Этот глоссарий задаёт язык пользовательской документации. Он не заменяет
нормативные контракты, но помогает отличать точный технический идентификатор от
обычного пояснения на русском языке.

## Названия продукта, сохраняемые на английском

Названия модулей и итоговых документов сохраняются в канонической форме, когда
они обозначают конкретный пункт меню или конкретный документ: `Review Suite`,
`Architecture Review`, `Test Engineering`, `Code Quality Review`, `Test
Assurance`, `Test Plan`, `Contract Consistency Report`, `Service Simulator
Design`, `E2E Test Plan`.

При первом употреблении полезно дать русское пояснение. В дальнейшей прозе
используйте естественные русские слова, если речь идёт не о названии элемента
интерфейса.

## Точные токены и идентификаторы, сохраняемые без изменений

Не переводятся идентификаторы, имена файлов, пути, API, протоколов и значения
перечислений. Их следует заключать в обратные кавычки, если они встречаются в
обычной фразе.

```text
NEW, RESUME, REVALIDATE, EXTEND, USE_EXISTING, PROJECTION_REPAIR
STANDARD_FULL, FORENSIC
REVIEW_ONLY, REVIEW_PLUS_TARGET_ARCHITECTURE,
REVIEW_PLUS_TARGET_AND_ROADMAP
CURRENT, STALE, BLOCKED, VALID, REVALIDATION_REQUIRED, UNKNOWN
PERMISSIVE, REQUIRED_SCOPE_CURRENT, ALL_SCOPED_CURRENT
WS-*, EV-*, COMP-*, IF-*, INT-*, DS-*, EVENT-*, FLOW-*, AUTH-*, CFG-*, ERR-*
RF-*, BC-*, CC-*, MAT-*, TM-*, GAP-*, TASK-*, CQ-*, CQRA-*, PRJ-*, RG-*
```

## Предпочтительная русская терминология

В объяснениях используйте русские соответствия. Не превращайте внутренний
английский жаргон в обычный язык документации.

| Избегать в русской прозе | Предпочтительная форма |
|---|---|
| review | аудит, проверка, разбор |
| capability | модуль проверки |
| output | итоговый документ, результат |
| authority | источник истины, владелец смысла |
| semantic / semantic state | семантический / семантическое состояние |
| projection | проекция, представление |
| baseline | базовая ревизия, исходное состояние |
| workset | рабочая область исследования |
| observation | наблюдение |
| workflow | процесс, сценарий работы |
| package | пакет результатов |
| current / accepted / fresh | актуальный / принятый / подтверждённо актуальный |
| bounded / targeted | ограниченный по области / адресный |
| presentation | представление, оформление |
| owner / writer | владелец / компонент, имеющий право записи |
| lifecycle | жизненный цикл |
| handoff | передача состояния |
| scope | область, границы проверки |

## Основные понятия

| Термин | Значение |
|---|---|
| **Базовая ревизия** | Зафиксированное состояние проекта, относительно которого собираются доказательства и принимаются выводы. Обычно это Git-коммит; для незакоммиченного дерева может использоваться явно обозначенный временный снимок. |
| **Модуль проверки** | Независимый модуль `Review Suite`: `Architecture Review`, `Test Engineering` или `Code Quality Review`. |
| **Область проверки** | Явно ограниченная система, подсистема, граница, поток или набор зависимостей, которые исследуются в данном запуске. |
| **Доказательство** | Наблюдение, привязанное к конкретному источнику и базовой ревизии. Само по себе оно не является выводом или техническим фактом. |
| **Рабочая область исследования** | Запись `WS-*`, объединяющая связанные наблюдения `EV-*`, ограничения и передачу состояния. |
| **Наблюдение** | Адресуемая запись `EV-*` внутри `WS-*`. |
| **Shared Technical Model (STM)** | Общая принятая модель существенных технических фактов системы. |
| **Источник истины** | Артефакт или процесс, который вправе хранить и изменять определённый вид смысла. |
| **Семантический источник истины** | Авторитетное техническое состояние: факты STM, `RF-*`, `BC-*`, `CQ-*` и другие записи модулей. |
| **Проекция** | Человекочитаемое или операционное представление принятого смысла. Проекция не становится источником истины только потому, что записана в Markdown. |
| **Происхождение вывода** | Цепочка от записи вывода через STM или доказательство к исходному коду либо внешнему источнику. |
| **Вывод** | Принятое и доказанное замечание конкретного модуля. `Architecture Review` использует `RF-*`, `Code Quality Review` — `CQ-*`. |
| **Кандидат** | Предварительная гипотеза до решения владеющей проверки. Кандидат не является источником истины. |
| **Полнота охвата** | Насколько выбранная область действительно исследована и подтверждена достаточными доказательствами. |
| **Актуальность** | Соответствие записи её зависимостям и базовой ревизии. Актуальность семантики и актуальность проекции проверяются отдельно. |
| **Зависимость** | Явная связь одной семантической записи или проекции с другой; используется для адресной повторной проверки и закрытия пакета. |
| **Пакет результатов** | Именованный набор итоговых проекций, проверяемый как единая поставка. |
| **Повторная проверка** | Проверка затронутой изменениями части семантической модели. Не равна полному повторному аудиту. |
| **Пересборка** | Создание свежей проекции из уже принятого смысла в отдельном запуске `RG-*`. |
| **Замещение** | Явная связь, которой новая запись или ревизия заменяет старую без переписывания истории. |
| **Основной артефакт** | Артефакт, в котором действительно хранится соответствующий технический смысл или состояние процесса. |
| **Устойчивая граница** | Сохранённая точка процесса, с которой работу можно безопасно продолжить в другом сеансе. |
| **Передача состояния** | Компактная запись для передачи работы между агентами и этапами с точными ссылками на источники истины, базовую ревизию и открытые вопросы. |
| **Существенное последствие** | Практический эффект механизма: риск, дефект поведения, рост стоимости сопровождения или нарушение инварианта. |

## Практическое правило

Сначала объясните действие или состояние по-русски. Затем, если читателю нужен
точный технический ориентир, укажите канонический токен в обратных кавычках.
Например: «повторная проверка возвращает `FULL_REAUDIT_RECOMMENDED`, когда
адресное завершение больше нельзя считать надёжным».
