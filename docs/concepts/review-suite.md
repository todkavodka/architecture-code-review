# Review Suite

`Review Suite` объединяет три независимых модуля проверки. Они используют общие
доказательства и Shared Technical Model, но сохраняют собственные источники
технического смысла.

## Три модуля проверки

### Architecture Review

Отвечает на вопросы:

- как система реально устроена;
- где проходят существенные границы выполнения и доверия;
- кто владеет состоянием и ресурсами;
- как устроены жизненный цикл, конкурентное выполнение, повторы, восстановление и обработка отказов;
- какие архитектурные корневые выводы подтверждены;
- какие `Target Architecture` и `Remediation Roadmap` нужны, если они запрошены.

Источники технической истины: `RF-*` и другие записи, принадлежащие `Architecture Review`.

### Test Engineering

Отвечает на вопросы:

- какие существенные поведения должны быть доказаны;
- какие из них действительно подтверждаются исполняемыми тестами;
- где недостаточно тестовых доказательств;
- расходятся ли представления `DECLARED` / `IMPLEMENTED` / `CONSUMED` / `TESTED`;
- какие `Test Plan`, проект тестовой среды, имитатор сервиса или `E2E Test Plan` нужны;
- какие негативные и граничные API-сценарии нужно доказать, если в области есть API input robustness.

Источники технической истины: `BC-*`, `CC-*`, `MAT-*`, `TM-*`, `GAP-*`, `TASK-*`.
Сгенерированный или принятый тестовый случай остаётся описанием того, что надо доказать, и не создаёт `TESTED` без принятых доказательств фактического исполнения.

### Code Quality Review

Ищет не стилистические предупреждения сами по себе, а механизмы реализации с доказуемым существенным последствием для сопровождения, надёжности, тестируемости, конкурентного выполнения, зависимостей, жизненного цикла ресурсов и других качеств. Сюда входит и API input robustness: отсутствие или неясность лимитов, порядок materialization/validation, обход схемы и другие механизмы, способные привести к избыточному потреблению ресурсов или недоказанной защите входа.

Источники технической истины: `CQ-*` и `CQRA-*`.

## Requested Work: что действительно выбрал пользователь

Для `NEW` интерфейс по-прежнему показывает три основных модуля:

```text
[ ] Architecture Review
[ ] Test Engineering
[ ] Code Quality Review
```

Но валидность запроса определяется не старым правилом «обязательно выбрать хотя бы один модуль», а наличием подтверждённой работы в `Requested Work`.

Допустимы:

```text
capability-only
standalone-output-only
mixed
```

Недопустимы:

```text
нет выбранного capability и нет самостоятельного output/view
только Product context без Requested Work
```

`Requested Work` — это подтверждённые пользователем модули и/или допустимые самостоятельные результаты/представления. `Resolved Work` — внутренний минимальный набор зависимостей, который инструмент должен разрешить для выполнения запроса. Эти понятия не равны:

```text
requested_work != resolved_work
internal dependency != selected capability
```

`Architecture Review` не является обязательным родителем для `Test Engineering` или `Code Quality Review`. Если другому модулю или самостоятельному результату нужна принятая часть STM, она разрешается как внутренняя зависимость и не считается автоматически выбранным `Architecture Review`.

## Настройка модуля и выбор документов — разные вещи

Выбор модуля определяет, какая семантическая работа должна быть выполнена. Выбор итоговых документов определяет, какие представления нужны пользователю. Некоторые результаты принадлежат конкретному capability и при прямом запросе нормализуются к своему владельцу; другие допустимы как самостоятельные output/view-запросы.

Например:

```text
Code Quality Review: ON
  Findings View: ON
  Summary: OFF
  Hotspots: OFF
  Roadmap Contribution: OFF
```

означает, что выполняется анализ качества реализации, но пользователь заказал только один человекочитаемый итоговый документ.

Прямой запрос `Maintainability Hotspots` или `Code Quality Summary` остаётся результатом, принадлежащим `Code Quality Review`, и нормализуется к этому модулю, а не превращается в новый самостоятельный источник смысла.

## Architecture: две независимые оси

`Architecture Review` имеет две независимые оси: глубину исследования и конечный результат:

```text
Depth:
  STANDARD_FULL
  FORENSIC

Endpoint:
  REVIEW_ONLY
  REVIEW_PLUS_TARGET_ARCHITECTURE
  REVIEW_PLUS_TARGET_AND_ROADMAP
```

Любая глубина поддерживает любой конечный результат. `FORENSIC` не означает `REVIEW_ONLY`.

## Конфигурация модуля и подтверждение

Выбранный модуль не означает, что его конфигурация уже завершена. В NEW
каждый выбранный capability получает состояние UNRESOLVED; его меню должно
явно разрешить применимые параметры и результаты. Для Test Engineering
Test Assurance обязателен, а все дополнительные результаты отмечаются как
выбранные или не выбранные. Для Code Quality Review каждый из четырёх
результатов разрешается отдельно; допустимый нулевой набор требует явного
подтверждения.

Standalone outputs относятся только к самостоятельным представлениям и не
заменяют конфигурацию выбранного capability. Перед CONFIRMED Requested Work
инструмент показывает сводку с областью, capability-конфигурацией,
standalone outputs и внутренними зависимостями только для чтения. Без
REQUESTED_WORK_CONFIGURATION_COMPLETE содержательная работа не начинается.

## Общий фактический фундамент

Модули проверки не должны независимо «изобретать» систему каждый для себя.

```text
Исходные источники
  -> Общие доказательства
  -> Shared Technical Model
       |        |        |
       v        v        v
 Архитектура  Тестовая инженерия  Качество кода
```

Общий слой хранит наблюдения и факты. Слой модулей проверки хранит интерпретации и решения в своих областях.

Для API input robustness это особенно важно: факты об интерфейсе и доказательства ограничений остаются в общем фактическом слое/Stage F, Code Quality интерпретирует качество реализации, а Test Engineering формулирует, что необходимо доказать тестами.

## Когда модули проверки взаимодействуют

Один механизм может иметь несколько независимых последствий.

Например:

```text
INT-014 публикация после фиксации
  |
  +--> RF-007 неоднозначность владения в архитектуре
  +--> GAP-004 нет доказательства повторных попыток и конкурентности
  +--> CQ-012 дублирующий механизм повторных попыток
```

Это не дублирование. Каждая запись отвечает на свой вопрос и имеет отдельный жизненный цикл.

## Stack Addenda

Дополнения для конкретных языков и фреймворков уточняют анализ, но не являются основными модулями проверки. Они не создают новый источник технической истины и не должны молча включать модуль проверки.

## Что происходит после выбора

Для `NEW` последовательность концептуально такая:

```text
базовая ревизия
-> Requested Work
-> разрешение Resolved Work / внутренних зависимостей
-> создание сохранённой начальной STM
-> минимально необходимая часть доказательств и модели
-> работа выбранных владельцев семантики
-> стабилизация семантического состояния
-> анализ влияния на проекции
-> определение состава пакета
-> запрошенные итоговые документы
```
