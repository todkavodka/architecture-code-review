# Доказательства и Shared Technical Model

Этот документ объясняет, как инструмент превращает чтение репозитория и внешних
источников в повторно используемые технические факты.

## Зачем разделять доказательства и факты

Если сразу превращать наблюдение из кода в вывод, теряется важная граница:

```text
что источник показал
!=
что это означает для архитектуры, тестов или качества кода
```

Поэтому цепочка фактических данных состоит минимум из двух уровней:

```text
Source
  -> Shared Evidence
  -> Shared Technical Model
```

Только после этого модуль проверки создаёт собственную интерпретацию.

## Shared Evidence

### `WS-*`

`WS-*` — ограниченная по области исследовательская работа. Она задаёт границы одного прохода исследования и физически группирует наблюдения.

Минимально рабочая область фиксирует:

- устойчивый идентификатор;
- область;
- базовую ревизию;
- состояние;
- исследованные источники;
- ограничения;
- наблюдения `EV-*`;
- краткую передачу состояния.

У одной рабочей области есть одна сторона, имеющая право записи. Это снижает риск, что несколько агентов одновременно перепишут одно и то же сохранённое состояние доказательств.

### `EV-*`

`EV-*` — логически адресуемое наблюдение внутри рабочей области.

Пример:

```text
WS-012-payment-retry#EV-003

source: src/payment/retry.py
symbol: RetryCoordinator.complete
baseline: 7f3a1c2
observed: состояние сохраняется до публикации события завершения
```

`EV-*` не назначает серьёзность, не говорит «это ошибка» и не выбирает способ устранения. Он фиксирует только наблюдение, ограниченное имеющимися доказательствами.

## Привязка к базовой ревизии

Доказательство всегда связано с базовой ревизией. Старое наблюдение нельзя переписать так, чтобы оно выглядело актуальным для нового коммита.

Если исходный код изменился:

1. старое наблюдение сохраняется как историческое доказательство;
2. анализ влияния определяет, нужны ли новые доказательства;
3. при необходимости создаётся новое наблюдение, связанное с новой ревизией;
4. зависимая семантика проходит повторную проверку.

Так сохраняется история того, почему был принят прошлый вывод.

## Shared Technical Model

STM хранит принятые общие технические факты.

Основные families:

```text
COMP-*    Component / Runtime Unit
IF-*      Interface
INT-*     Interaction
DS-*      Data Store
EVENT-*   Event / Message
FLOW-*    Material Flow
AUTH-*    Auth / Trust Boundary
CFG-*     Configuration Fact
ERR-*     Error / Failure Contract
```

Факт STM отвечает на вопрос «что материально существует или происходит в системе?».

Он не отвечает:

- является ли это defect;
- достаточно ли это протестировано;
- насколько это плохо реализовано;
- что исправлять первым.

## Identity и revision

Stable identity используется, пока речь идёт о той же семантической сущности.

Например:

```text
IF-021@rev1
IF-021@rev2
IF-021@rev3
```

означает ревизии одного интерфейса.

Если смысл сущности изменился настолько, что это уже другой object identity, старую запись не переписывают. Создаётся новая identity и явная связь supersession.

Это важно для повторной проверки: последующие записи могут зависеть от конкретного идентификатора и ревизии, а не только от имени файла.

## Relations

STM использует controlled relation vocabulary, например:

```text
PROVIDES
CONSUMES
CALLS
PUBLISHES
SUBSCRIBES
READS_FROM
WRITES_TO
OWNS_STATE
PROTECTED_BY
CONFIGURED_BY
EMITS_ERROR
PARTICIPATES_IN
DEPLOYS_AS
DEPENDS_ON
```

Связи делают модель пригодной для обхода зависимостей и анализа влияния.

## Technical Model Gate

Принятую семантику STM меняет только Technical Model Gate.

Модуль проверки может сообщить:

```text
TECH_FACT_CANDIDATE
TECH_FACT_CONFLICT
TECH_FACT_REVALIDATION_REQUEST
```

но не должен напрямую переписывать принятые записи STM.

Это особенно важно, если `Architecture Review` и `Test Engineering` видят один факт по-разному: спор решается на уровне источника фактической истины, а не победой «последнего записавшего».

## Multiple observed views

Один технический объект может иметь несколько representations:

```text
DECLARED
IMPLEMENTED
CONSUMED
TESTED
```

Например, OpenAPI говорит одно, backend реализует другое, frontend ожидает третье, а тесты проверяют четвёртое.

STM может сохранить эти наблюдаемые представления, но не выбирает автоматически «правильную» сторону. Когда требуется решение об источнике истины, его принимает соответствующая специализированная проверка, например `Contract Verification`.

## Полнота охвата

Создание сохранённой STM не означает полного описания репозитория.

```text
always create model
!=
always build complete model
```

Требуемая ширина зависит от последующего решения.

Полный `Architecture Review` требует принятого фактического охвата, достаточного для архитектурных утверждений. Ограниченный по области `Code Quality Review` может использовать принятую часть модели.

Если охват неполный, последующее утверждение должно учитывать это ограничение. Инструмент не должен формулировать глобальный вывод, если доказательства были локальными.

## Как читать факт до source

Типичный provenance path:

```text
семантический вывод
  -> факт STM
  -> WS#EV
  -> raw source
```

Иногда семантическая запись может ссылаться прямо на доказательство, если отдельная сущность STM не нужна. Главное — сохранить точное происхождение, привязанное к базовой ревизии.

## Что происходит при конфликте

Если зависимый модуль проверки обнаруживает, что принятый факт больше не подходит:

```text
TECH_FACT_CONFLICT
or
TECH_FACT_REVALIDATION_REQUEST
```

До согласования нельзя использовать спорный необходимый факт как принятую техническую истину для последующей работы.

При этом не связанная с конфликтом принятая работа не обязана автоматически открываться заново.
