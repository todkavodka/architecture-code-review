# Обновление и возврат к предыдущей версии

Этот документ описывает обновление репозитория Skill и возврат к ранее
известной рабочей ревизии. Он не заменяет правила для сохранённых пакетов
аудита: подробные ограничения совместимости и согласования приведены в
[документе о совместимости и миграции](compatibility-and-migration.md).

Обновление меняет доступные для последующих сеансов инструменты, контракты и
документацию Skill. Оно не подтверждает автоматически, что прежний пакет
аудита по-прежнему пригоден для текущей базовой ревизии анализируемого проекта.

## До обновления

Определите текущую ревизию Skill и состояние его рабочего дерева:

```bash
cd ~/.agents/skills/architecture-code-review
git status --short
git branch --show-current
git rev-parse HEAD
```

Запишите SHA текущей ревизии и SHA или тег целевой ревизии, если он выбран.
Сохраните нужные незакоммиченные изменения и относящееся к задаче состояние
аудита. Не предполагайте, что Git хранит внешние файлы, ручные изменения
семантических артефактов или более поздние созданные представления.

Если в рабочем дереве есть отслеживаемые изменения, сначала установите их
происхождение и выберите безопасный способ сохранить работу: отдельную ветвь
или форк, либо перенос изменений в отдельный патч. Не используйте
`git reset --hard` или `git clean` как обычный способ подготовить установку к
обновлению. Неотслеживаемые файлы также не следует уничтожать только ради
обновления.

Перед массовым обновлением зафиксируйте также предполагаемую целевую ревизию,
проверьте заметки об изменениях, если они опубликованы, и оцените изменения
контрактов. В частности, выясните, затрагивают ли они толкование смысла,
схему или значение артефактов, правила процесса, контракты представлений либо
требования к пакету результатов. Формальная матрица совместимости для каждой
пары ревизий не определена; не рассчитывайте на автоматическое преобразование
состояния или на совместимость по номеру версии.

## Обновление ветви `main`

Когда рабочее дерево чисто и требуется текущая ветвь `main`, выполните:

```bash
git fetch origin --prune
git switch main
git pull --ff-only
```

`--ff-only` сохраняет установку воспроизводимой: автоматическое слияние
локальных изменений с полученной ревизией может создать непроверенное сочетание
контрактов. Если перемещение вперёд невозможно, остановитесь и разберите
причину расхождения истории; не заменяйте это разрушительной очисткой дерева.

Для воспроизводимой командной среды допустимо закрепить известную рабочую
ревизию:

```bash
git checkout <known-good-sha>
```

Храните точный SHA Skill рядом с правилами управления пакетами аудита и, когда
это существенно, с базовой ревизией проверяемого проекта. Это практическая
фиксация окружения, а не гарантия семантической совместимости.

После смены ревизии начните новый сеанс агента и проверьте следующее:

1. `git rev-parse HEAD` возвращает ожидаемый SHA;
2. нужные файлы Skill и `SKILL.md` доступны агенту;
3. для существующего пакета выполнено обычное начальное обнаружение, а не
   безусловный запуск `NEW`;
4. можно установить, читаются ли владеющие артефакты и их сохранённое состояние
   в текущих контрактах;
5. определено, нужны ли `REVALIDATE`, анализ влияния на проекции или иной
   предусмотренный маршрут.

Успешный `git pull` сам по себе не завершает эту проверку.

## Существующий пакет после обновления

Ревизия Skill, базовая ревизия проверяемого репозитория и ревизия пакета
аудита — разные объекты. Пакет находится в анализируемом репозитории и может
сохраниться после обновления Skill, но существование сохранённого файла не
доказывает его актуальность.

Если изменилась базовая ревизия проекта или её зависимости, может понадобиться
`REVALIDATE` в соответствии со [справочником процессов](../reference/workflows.md).
Само обновление Skill не превращает прежние результаты в актуальные и не
подменяет повторную проверку. Полные правила жизненного цикла и актуальности
описаны в [соответствующем разделе](../concepts/lifecycle-and-freshness.md).

Если изменение затрагивает представления, сначала определите его последствия.
Анализ влияния на проекции не является их повторным построением: при
необходимости пересборка выполняется отдельной работой `RG-*`. Пересборка не
устраняет неоднозначность семантического состояния или контракта. Если владелец
смысла, классификация представления или его контракт неясны, остановитесь и
направьте случай на `CONTRACT_ADJUDICATION`; не пытайтесь «проверить»
совместимость повторным построением.

Представление не становится семантическим источником истины из-за того, что оно
сохранено или создано позднее. При расхождении исправляйте или повторно
проверяйте владеющий семантический артефакт по подходящему маршруту; не
изменяйте сгенерированное представление, чтобы подогнать его под ожидания.
Подробные правила для представлений и пакетов приведены в
[документе о проекциях и пакетах](../concepts/projections-and-packages.md).

Старый пакет не считается повреждённым только из-за отсутствия новых полей.
Однако его нельзя молча истолковывать как современное подтверждённо актуальное
состояние. При неоднозначной или неподдерживаемой миграции процесс должен
остановиться для ручного согласования, а не угадывать преобразование.

## Проверка обновления в нескольких установках

До широкого обновления проверьте целевую ревизию на представительных пакетах:
незавершённом, принятом, устаревшем и старом пакете без современных метаданных.
Проверьте обнаружение Skill, чтение контрактов и маршрут, который требуется
для каждого пакета. Это проверка процесса и совместимости на выбранных
примерах, а не обещание общей обратной совместимости или автоматической
миграции.

## Возврат к предыдущей ревизии Skill

Если новая ревизия Skill выявила неисправность или несовместимость с вашим
процессом, вернитесь к заранее записанной известной рабочей ревизии:

```bash
cd ~/.agents/skills/architecture-code-review
git fetch origin --prune
git checkout <previous-known-good-sha>
```

Затем начните новый сеанс агента. Такой переход восстанавливает более ранний
набор реализации и контрактов самого Skill. Он не возвращает автоматически
назад базовую ревизию анализируемого проекта, внешние файлы, вручную изменённые
семантические артефакты, созданные позднее представления или изменения вне Git.
Для них требуется самостоятельное восстановление из сохранённых источников,
если оно вообще возможно.

После возврата проверьте:

1. `git rev-parse HEAD` показывает ожидаемую ревизию;
2. рабочее дерево и отдельно сохранённая работа не были утрачены;
3. не перепутаны ревизия Skill и базовая ревизия проверяемого проекта;
4. сохранённый пакет всё ещё можно истолковать по активным контрактам;
5. представления не объявлены актуальными без отдельной проверки их
   актуальности и, при необходимости, явной пересборки;
6. необходимость повторной проверки, анализа влияния на проекции или
   согласования контрактов определена явно.

Возврат к более ранней ревизии не удаляет автоматически артефакты нового
формата и не отменяет изменения, которые новая ревизия уже внесла в пакет.
Оценивайте такой пакет отдельно по истории ревизий и владеющим артефактам.

## Возврат с закреплённой ревизии на `main`

```bash
git switch main
git pull --ff-only
```

После этого повторите проверки, перечисленные в разделе «До обновления» и
после команды обновления. При неудачном обновлении или возврате используйте
[диагностику проблем](troubleshooting.md); она не заменяет проверку
совместимости и состояния пакета.
