# Обновление самого skill и возврат к предыдущей версии

Этот документ описывает **обновление установленного `architecture-code-review`** и возврат к ранее известной рабочей ревизии самого skill.

Он **не** описывает изменение исходного кода анализируемого проекта. Если изменился проверяемый repository, branch, commit, pull request, dependency или configuration и нужно обновить audit state, используйте руководство [Что делать после изменения кода](../guides/after-code-changes.md).

Полезно различать три независимых объекта:

```text
ревизия architecture-code-review skill
ревизия анализируемого source
ревизия / состояние audit package
```

Обновление одного из них не обновляет два остальных автоматически.

Этот документ также не заменяет правила для сохранённых пакетов аудита: подробные ограничения совместимости и согласования приведены в [документе о совместимости и миграции](compatibility-and-migration.md).

Обновление skill меняет доступные для последующих сеансов правила, контракты и пользовательскую документацию. Оно не подтверждает автоматически, что прежний пакет аудита по-прежнему пригоден для текущей базовой ревизии анализируемого проекта.

## До обновления

Определите текущую ревизию skill и состояние его рабочего дерева:

```bash
cd ~/.agents/skills/architecture-code-review
git status --short
git branch --show-current
git rev-parse HEAD
```

Запишите SHA текущей ревизии и SHA или тег целевой ревизии, если он выбран. Сохраните нужные незакоммиченные изменения и относящееся к задаче состояние аудита. Не предполагайте, что Git хранит внешние файлы, ручные изменения семантических артефактов или более поздние созданные представления.

Если в рабочем дереве есть отслеживаемые изменения, сначала установите их происхождение и выберите безопасный способ сохранить работу: отдельную ветвь или форк, либо перенос изменений в отдельный патч. Не используйте `git reset --hard` или `git clean` как обычный способ подготовить установку к обновлению. Неотслеживаемые файлы также не следует уничтожать только ради обновления.

Перед массовым обновлением зафиксируйте предполагаемую целевую ревизию, проверьте заметки об изменениях, если они опубликованы, и оцените изменения контрактов. В частности, выясните, затрагивают ли они толкование смысла, схему или значение артефактов, правила процесса, контракты представлений либо требования к пакету результатов.

Формальная матрица совместимости для каждой пары ревизий не определена. Не рассчитывайте на автоматическое преобразование состояния только по номеру версии.

## Обновление ветви `main`

Когда рабочее дерево чисто и требуется текущая ветвь `main`, выполните:

```bash
git fetch origin --prune
git switch main
git pull --ff-only
```

`--ff-only` сохраняет установку воспроизводимой: автоматическое слияние локальных изменений с полученной ревизией может создать непроверенное сочетание контрактов.

Если fast-forward невозможен, остановитесь и разберите причину расхождения истории. Не заменяйте это разрушительной очисткой дерева.

Для воспроизводимой командной среды допустимо закрепить известную рабочую ревизию:

```bash
git checkout <known-good-sha>
```

Храните точный SHA skill рядом с правилами управления пакетами аудита и, когда это существенно, с базовой ревизией проверяемого проекта. Это фиксация окружения, а не гарантия семантической совместимости.

После смены ревизии начните новый сеанс агента и проверьте:

1. `git rev-parse HEAD` возвращает ожидаемый SHA;
2. `SKILL.md` и нужные файлы доступны агенту;
3. для существующего пакета выполняется обычное начальное обнаружение, а не безусловный `NEW`;
4. владеющие артефакты читаются по текущим контрактам;
5. определено, нужны ли migration, `REVALIDATE`, projection impact или другой предусмотренный маршрут.

Успешный `git pull` сам по себе не завершает эту проверку.

## Что обновление skill не делает

Обновление `architecture-code-review` не означает автоматически, что:

- анализируемый проект изменился;
- его accepted baseline нужно продвинуть;
- findings стали stale;
- findings стали current;
- старые projections нужно пересобрать;
- legacy package успешно мигрировал;
- Product baseline изменился;
- нужно запустить новый полный аудит.

Эти решения принимаются отдельно на основании состояния audit package и анализируемого source.

## Существующий пакет после обновления

Ревизия skill, базовая ревизия проверяемого репозитория и ревизия пакета аудита — разные объекты. Пакет находится в анализируемом репозитории и может сохраниться после обновления skill, но существование сохранённого файла не доказывает его актуальность.

Если изменилась базовая ревизия проекта или её зависимости, может понадобиться `REVALIDATE` в соответствии со [справочником процессов](../reference/workflows.md) и руководством [Что делать после изменения кода](../guides/after-code-changes.md).

Само обновление skill не превращает прежние результаты в актуальные и не подменяет повторную проверку.

Полные правила жизненного цикла и актуальности описаны в [соответствующем разделе](../concepts/lifecycle-and-freshness.md).

## Представления после обновления skill

Если новая версия skill меняет contracts или presentation rules, сначала определите влияние на существующие проекции.

Анализ влияния на проекции не является их повторным построением. При необходимости пересборка выполняется отдельной работой `RG-*`.

Пересборка не устраняет неоднозначность semantic state или contract. Если владелец смысла, классификация представления или его contract неясны, остановитесь и направьте случай на `CONTRACT_ADJUDICATION`, а не пытайтесь «проверить» совместимость повторным построением.

Представление не становится семантическим источником истины из-за того, что оно сохранено или создано позднее.

При расхождении исправляйте или повторно проверяйте владеющий semantic artifact по подходящему маршруту; не изменяйте сгенерированный документ, чтобы подогнать его под ожидания.

Подробные правила: [Проекции и пакеты](../concepts/projections-and-packages.md).

## Старые пакеты без новых полей

Старый пакет не считается повреждённым только из-за отсутствия новых полей.

Однако его нельзя молча истолковывать как современное подтверждённо актуальное состояние.

Например, отсутствие современного lifecycle поля finding не означает автоматически `ACTIVE` или `RESOLVED`.

При неоднозначной или неподдерживаемой migration процесс должен остановиться для ручного согласования, а не угадывать преобразование.

Подробно: [Совместимость и миграция](compatibility-and-migration.md).

## Проверка обновления в нескольких установках

До широкого обновления проверьте целевую ревизию на представительных пакетах:

- незавершённом;
- принятом;
- устаревшем;
- legacy package без современных metadata.

Проверьте обнаружение skill, чтение контрактов и маршрут, который требуется для каждого пакета.

Это проверка процесса и совместимости на выбранных примерах, а не обещание общей обратной совместимости или автоматической migration.

## Возврат к предыдущей ревизии skill

Если новая ревизия выявила неисправность или несовместимость с вашим процессом, вернитесь к заранее записанной рабочей ревизии:

```bash
cd ~/.agents/skills/architecture-code-review
git fetch origin --prune
git checkout <previous-known-good-sha>
```

Затем начните новый сеанс агента.

Такой переход восстанавливает более ранний набор реализации и контрактов самого skill. Он не возвращает автоматически:

- базовую ревизию анализируемого проекта;
- внешние файлы;
- вручную изменённые semantic artifacts;
- созданные позднее projections;
- изменения вне Git.

Для них требуется самостоятельное восстановление из сохранённых источников, если оно возможно.

После возврата проверьте:

1. `git rev-parse HEAD` показывает ожидаемую ревизию;
2. рабочее дерево и отдельно сохранённая работа не были утрачены;
3. не перепутаны ревизия skill и baseline проверяемого проекта;
4. сохранённый пакет всё ещё можно истолковать по активным контрактам;
5. projections не объявлены актуальными без отдельной проверки;
6. необходимость revalidation, projection impact или contract adjudication определена явно.

Возврат к более ранней ревизии не удаляет автоматически артефакты нового формата и не отменяет изменения, которые новая ревизия уже внесла в пакет.

## Возврат с закреплённой ревизии на `main`

```bash
git switch main
git pull --ff-only
```

После этого повторите проверки из раздела «До обновления».

При неудачном обновлении или возврате используйте [Диагностику проблем](troubleshooting.md). Она не заменяет проверку совместимости и состояния пакета.
