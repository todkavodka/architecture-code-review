# Пример: архитектурный аудит сервиса заказов

Ниже — сквозной пример `Architecture Review` перед модернизацией существующего сервиса заказов. Пути, идентификаторы и названия компонентов условные, но логика примера соответствует модели skill.

## Исходная ситуация

У команды есть серверное приложение с неполной документацией. После тайм-аута публикации иногда появляются два события о завершении одного заказа.

Команда хочет понять:

- как на самом деле устроен путь завершения заказа;
- где находится корневая причина дублирования;
- насколько проблема серьёзна;
- как должна выглядеть целевая архитектура;
- в каком порядке безопасно исправлять систему.

Запрос:

```text
Используй architecture-code-review.
Нужен Architecture Review сервиса заказов.
Найди корневую причину дублирующих completion events.
Глубина FORENSIC, результат с Target Architecture и Remediation Roadmap.
```

## Шаг 1. Начальное состояние

Skill обнаруживает:

```text
repository: orders-service
baseline: a1b2c3d
existing audit package: отсутствует
working tree: чистый
```

Для новой работы выбирается `NEW`.

В Review Suite включается только Architecture Review:

```text
Architecture Review: ON
  Depth: FORENSIC
  Endpoint: REVIEW_PLUS_TARGET_AND_ROADMAP

Test Engineering: OFF
Code Quality Review: OFF
```

`FORENSIC` здесь оправдан неоднозначным тайм-аутом, повторными попытками и необходимостью понять реальное владение публикацией события.

## Шаг 2. Сбор доказательств

Исследование разбивается на ограниченные рабочие области:

```text
WS-001-runtime-topology
WS-002-order-state
WS-003-completion-publication
WS-004-timeout-retry
WS-005-shutdown-recovery
```

В `WS-003` фиксируются наблюдения:

```text
EV-004
source: src/orders/service.py
symbol: complete_order
observed:
  транзакция заказа фиксируется до вызова публикации completion event

EV-007
source: src/events/publisher.py
symbol: publish_completion
observed:
  timeout не позволяет установить, принял брокер сообщение или нет
```

В `WS-004`:

```text
EV-003
source: src/workers/retry.py
observed:
  после неоднозначного timeout повторная попытка снова вызывает publish_completion
```

Это ещё не архитектурные findings. Это только наблюдения, привязанные к конкретному source state.

## Шаг 3. Shared Technical Model

Из доказательств принимается необходимая фактическая модель:

```text
COMP-API
COMP-WORKER
DS-ORDERS
EVENT-ORDER-COMPLETED
INT-COMPLETE-TRANSACTION
INT-PUBLISH-COMPLETION
FLOW-ORDER-COMPLETION
```

Она показывает существенный поток:

```text
завершение заказа
    ↓
фиксация транзакции
    ↓
публикация события
    ↓
неоднозначный timeout
    ↓
повторная попытка публикации
```

На этом этапе зафиксировано, **что происходит**, но архитектурный вывод ещё не принят.

## Шаг 4. Проверка возможных защитных механизмов

Перед принятием finding проверяются альтернативные объяснения и защитные механизмы:

- есть ли idempotency key;
- выполняет ли брокер дедупликацию;
- есть ли outbox;
- дедуплицирует ли consumer;
- существует ли единый владелец retry;
- фиксируется ли публикация как отдельное состояние;
- можно ли после timeout однозначно определить исход первой попытки.

Допустим, проверка показывает, что ни один механизм не обеспечивает системную уникальность публикации.

## Шаг 5. Архитектурный finding

Принимается:

```text
RF-007
lifecycle: ACTIVE
severity: HIGH

корневая граница:
  владение окончательной публикацией completion event

механизм:
  фиксация заказа и публикация события разделены;
  неоднозначный timeout не имеет устойчивого результата;
  retry повторяет публикацию без единого idempotent owner

последствие:
  один логический переход заказа может породить несколько
  наблюдаемых completion events

основание:
  INT-PUBLISH-COMPLETION@rev2
  WS-003#EV-007
  WS-004#EV-003
```

Цепочка происхождения:

```text
src/events/publisher.py@a1b2c3d
  ↓
WS-003#EV-007
  ↓
INT-PUBLISH-COMPLETION@rev2
  ↓
RF-007
```

Теперь это не просто предположение о коде, а принятый архитектурный вывод.

## Шаг 6. Target Architecture

Целевая архитектура должна отвечать именно на корневую причину.

Один из допустимых вариантов:

```text
транзакция заказа
    ↓
запись устойчивого намерения публикации в outbox
    ↓
один владелец доставки
    ↓
idempotency key
    ↓
повторная доставка без создания второго логического события
```

Важно: `Target Architecture` не становится фактом о текущей системе и не закрывает `RF-007`.

## Шаг 7. Remediation Roadmap

Дорожная карта может выглядеть так:

1. определить идентичность одного логического completion event;
2. добавить устойчивое состояние публикации;
3. перенести запись намерения публикации в ту же транзакционную границу, что и завершение заказа;
4. назначить единственного владельца доставки и retry;
5. добавить доказательства идемпотентности;
6. перевести потребителей на новый контракт;
7. проверить миграционный период;
8. только после этого удалить прежние прямые пути публикации.

Это план перехода, а не доказательство выполнения.

## Шаг 8. Итоговый пакет

После завершения в пакете остаются:

```text
baseline: a1b2c3d

доказательства:
  WS-001 ... WS-005
  EV-*

Shared Technical Model:
  COMP-*
  DS-*
  EVENT-*
  INT-*
  FLOW-*

Architecture Review:
  RF-007

человекочитаемые документы:
  Architecture Review
  Authoritative Findings Ledger
  Target Architecture
  Remediation Roadmap

working/INDEX.md:
  состояние процесса и ссылки на основные артефакты
```

Отчёт удобен для чтения, но источником смысла `RF-007` остаётся владеющая семантическая запись.

## Что происходит после исправления

Через неделю команда реализует outbox и idempotency key.

Сам commit не закрывает `RF-007`.

Если изменение ещё находится в PR:

```text
CHANGE_REVIEW
```

может показать:

```text
RF-007 → POTENTIALLY_RESOLVES
```

Но `RF-007` остаётся `ACTIVE`.

После принятия нового кода выполняется `REVALIDATE`:

```text
новый source state
    ↓
новые evidence
    ↓
повторная проверка INT-PUBLISH-COMPLETION
    ↓
owner revalidation RF-007
```

Только если доказано исчезновение корневой проблемы, Architecture Review принимает новую редакцию:

```text
RF-007 ACTIVE → RESOLVED
```

История finding при этом сохраняется.

## Что увидит пользователь в прогрессе

Если между baseline A и B других изменений findings нет:

```text
Current findings:
1 → 0

Resolved:
1

Historical registered:
1
```

То есть исторический finding не удаляется, но текущий риск уменьшается.
