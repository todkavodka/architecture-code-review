# Пример: проверка достаточности тестов

Этот пример показывает, как `Test Engineering` отличает большое количество проходящих тестов от реального доказательства важного поведения.

Пути, идентификаторы и числа условны, но логика соответствует модели skill.

## Исходная ситуация

В сервисе заказов есть 1200 тестов. Команда собирается изменить повторные попытки после тайм-аута и хочет понять, доказано ли следующее:

1. повторная попытка не создаёт второй заказ;
2. один логический заказ не создаёт несколько окончательных событий;
3. контракт повторного запроса одинаково понимают сервер, клиент и тесты.

Запрос:

```text
Используй architecture-code-review.
Нужен Test Engineering для retry flow заказа.
Подготовь Test Assurance, Test Plan и Contract Consistency Report.
Architecture Review и Code Quality Review не включай.
```

## Шаг 1. Конфигурация

Skill фиксирует baseline `a1b2c3d` и начинает `NEW`.

Выбрано:

```text
Test Engineering: ON
  Test Assurance: required
  Test Plan: selected
  Contract Consistency Report: selected

Architecture Review: OFF
Code Quality Review: OFF
```

Наличие 1200 тестов пока ничего не говорит о достаточности доказательств.

## Шаг 2. Доказательства

В рабочей области фиксируются наблюдения:

```text
WS-001-order-retry

EV-001
source: src/orders/handler.py
observed:
  транзакция заказа может успешно зафиксироваться до того,
  как ответ будет доставлен клиенту

EV-002
source: tests/test_retry.py
observed:
  test_retry_after_500 проверяет явный HTTP 500,
  но не потерю ответа после успешной фиксации

EV-003
source: api/openapi.yaml
observed:
  повторный client_order_id объявлен как HTTP 409
```

Из этого принимается нужный фактический срез Shared Technical Model:

```text
IF-ORDER-CREATE
INT-ORDER-COMMIT
ERR-CLIENT-RESPONSE-TIMEOUT
EVENT-ORDER-COMPLETED
```

## Шаг 3. Контракты поведения

Test Engineering формирует существенные поведения:

```text
BC-021
Повторная попытка после неоднозначного тайм-аута не создаёт второй заказ.

BC-022
Для одного поколения заказа наблюдаемо не более одного окончательного события.
```

Это не тесты. Это то, **что должно быть доказано**.

## Шаг 4. Цели проверки

Для этих поведений создаются цели:

```text
MAT-011
Доказать уникальность заказа, если commit прошёл,
а ответ клиенту был потерян.

MAT-012
Доказать уникальность completion event при повторной попытке.
```

## Шаг 5. Сопоставление с существующими тестами

Существующий тест:

```text
test_retry_after_500
```

действительно проходит. Но он проверяет другой случай:

```text
сервер явно вернул 500
```

а интересующий риск выглядит так:

```text
commit успешно выполнен
    ↓
ответ потерян
    ↓
клиент не знает результата
    ↓
повторяет запрос
```

Поэтому принимается:

```text
TM-031
relates_to: MAT-011
execution evidence: test_retry_after_500
verdict: PARTIAL
```

Тест существует и выполняется, но нужное поведение доказано только частично.

## Шаг 6. Пробелы в доказательствах

Принимаются:

```text
GAP-008
Для MAT-011 нет доказательства пути
«commit успешен, ответ потерян, клиент повторяет запрос».

GAP-009
Для MAT-012 нет доказательства уникальности completion event
при повторной попытке после неоднозначного timeout.
```

Это и есть основная ценность Test Engineering: не просто перечислить тесты, а показать, **какое важное поведение осталось недоказанным**.

## Шаг 7. Расхождение контракта

При сравнении представлений обнаруживается:

```text
DECLARED:
  OpenAPI → повторный client_order_id возвращает 409

IMPLEMENTED:
  сервер → возвращает существующий заказ с 200

CONSUMED:
  клиент → ожидает 200

TESTED:
  существующие тесты → проверяют 200
```

Создаётся:

```text
CC-004
status: CLASSIFIED
issue:
  представления контракта расходятся;
  требуется установить принятую семантику
```

Skill не решает автоматически, что OpenAPI «неправильный» или что код «неправильный». Сначала нужен owner decision.

## Шаг 8. Test Plan

На основе `GAP-008` и `GAP-009` формируется план доказательств.

Например:

```text
Case 1
  создать заказ
  позволить commit завершиться
  оборвать response до получения клиентом
  повторить тот же client_order_id
  проверить, что существует ровно один заказ

Case 2
  заставить broker принять completion event
  вернуть publisher timeout
  выполнить retry
  проверить, что наблюдаемо одно логическое completion event
```

Эти случаи ещё не являются доказательством.

```text
Test Plan != TESTED
```

## Шаг 9. Почему «тест написан» недостаточно

Допустим, инженер добавил:

```text
test_retry_after_lost_response
```

и закрыл задачу.

Это всё ещё не означает, что `GAP-008` закрыт.

Нужно:

```text
новый тест
    ↓
фактическое исполнение
    ↓
результат на нужном baseline и environment
    ↓
принятое execution evidence
    ↓
повторная проверка TM-*/GAP-*
```

Только после этого можно изменить семантическое состояние Test Engineering.

## Шаг 10. Итоговый Test Assurance

Краткое резюме может выглядеть так:

```text
TEST ASSURANCE: PARTIAL

BC-021
  частично доказан
  GAP-008 остаётся OPEN

BC-022
  не имеет достаточного execution evidence
  GAP-009 остаётся OPEN

Contract consistency
  CC-004 требует owner adjudication
```

Количество проходящих тестов при этом остаётся 1200+, но теперь ясно, что два существенных поведения всё ещё не доказаны.

## После изменения кода и тестов

После реализации нового retry-механизма и новых тестов не запускается новый `NEW`.

Используется `REVALIDATE`:

```text
изменился retry flow
    ↓
BC-021 / BC-022 затронуты
    ↓
MAT-011 / MAT-012 затронуты
    ↓
старые TM-* могут стать STALE
    ↓
получаются новые execution evidence
    ↓
GAP-008 / GAP-009 повторно оцениваются
```

Один gap может закрыться, а другой остаться открытым. Повторная проверка выполняется по каждому доказательству отдельно.
