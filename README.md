# Architecture Code Review

`architecture-code-review` — набор skills для глубокого инженерного анализа существующих программных систем. Он помогает не просто получить список замечаний, а построить проверяемую картину системы: связать выводы с исходным кодом и другими доказательствами, сохранить принятое состояние аудита и затем адресно обновлять его по мере изменения проекта.

Главный принцип:

> **Ширина утверждения не должна превышать ширину доказательств.**

Это не одноразовый генератор отчётов. Skill рассчитан на длительную работу: сегодня можно провести первичный аудит, через неделю проверить pull request, после merge переоценить только затронутые части, а через несколько месяцев расширить пакет новыми видами анализа, не начиная всё заново.

## Когда использовать

Skill полезен, когда нужно:

- восстановить фактическую архитектуру существующей системы;
- найти подтверждённые архитектурные корневые проблемы;
- понять, какие существенные поведения действительно доказаны тестами;
- найти пробелы в тестовых доказательствах и расхождения контрактов;
- провести Code Quality Review с привязкой к конкретным механизмам реализации;
- проверить ветку, commit или pull request относительно принятого состояния;
- оценить последствия изменений без полного повторного аудита;
- получить техническую документацию по уже исследованной системе;
- координировать аудит продукта, состоящего из нескольких репозиториев;
- сохранить историю находок и видеть текущий риск отдельно от уже закрытых проблем.

## Что входит в Review Suite

В Review Suite три независимых направления проверки.

### Architecture Review — архитектурная проверка

Восстанавливает фактическую архитектуру системы и проверяет:

- границы компонентов и владение состоянием;
- жизненный цикл ресурсов;
- конкурентное выполнение;
- интерфейсы и интеграции;
- границы доверия и авторизации;
- конфигурацию;
- отказоустойчивость и восстановление;
- корневые архитектурные проблемы и их последствия.

Дополнительно можно получить целевую архитектуру и дорожную карту исправлений.

### Test Engineering — инженерная проверка тестов

Определяет:

- какие существенные поведения системы известны;
- какие из них действительно подтверждены исполняемыми тестами;
- где тестовое доказательство отсутствует или недостаточно;
- согласованы ли объявленный контракт, реализация, потребители и тесты;
- какие Test Plan, Test Environment, Service Simulator или E2E-сценарии нужны.

Важно: сгенерированный тестовый случай не означает `TESTED`. Для такого утверждения нужны принятые доказательства фактического исполнения теста на нужной ревизии и в нужном окружении.

### Code Quality Review — проверка качества реализации

Ищет не косметические замечания, а конкретные механизмы реализации с доказуемым последствием для:

- сопровождаемости;
- надёжности;
- тестируемости;
- конкурентности;
- жизненного цикла ресурсов;
- зависимостей;
- локализации;
- обработки входных данных;
- других существенных свойств кода.

Например, наличие `maxLength` у JSON-поля само по себе не доказывает защиту от слишком большого запроса, если приложение успевает целиком прочитать тело в память до проверки схемы.

Три направления можно запускать вместе или по отдельности. Ни одно из них не является обязательным родителем другого.

## Установка

Для Codex, OpenCode и других агентов, использующих `~/.agents/skills`:

```bash
git clone \
  https://github.com/todkavodka/architecture-code-review.git \
  ~/.agents/skills/architecture-code-review
```

После установки начните новый сеанс агента.

Проверить установленную ревизию:

```bash
git -C ~/.agents/skills/architecture-code-review rev-parse HEAD
```

Подробности: [Установка](docs/getting-started/installation.md).

## Самый простой запуск

Откройте агент в корне анализируемого проекта и напишите:

```text
Используй architecture-code-review для этого проекта.
```

Skill сначала определит:

1. какой репозиторий или набор репозиториев выбран;
2. какая базовая ревизия анализируется;
3. существует ли уже пакет аудита;
4. можно ли переиспользовать ранее принятые результаты;
5. какой сценарий работы подходит к текущей ситуации.

Он не должен автоматически начинать новый полный аудит только потому, что пользователь снова вызвал skill.

Подробный первый запуск: [Быстрый старт](docs/getting-started/quick-start.md) и [Первый полный аудит](docs/getting-started/first-review.md).

## Жизненный цикл работы

В упрощённом виде работа выглядит так:

```text
первый запуск
    ↓
обнаружение существующего состояния
    ↓
выбор нужной работы
    ↓
сбор доказательств
    ↓
Shared Technical Model
    ↓
Architecture / Test Engineering / Code Quality
    ↓
принятые семантические записи
    ↓
человекочитаемые отчёты и техническая документация
    ↓
изменение исходного кода
    ↓
CHANGE_REVIEW или REVALIDATE
    ↓
адресная повторная проверка
    ↓
новое принятое состояние
```

Подробно: [Жизненный цикл аудита](docs/guides/audit-lifecycle.md).

## Что делать после изменения кода

Главный вопрос — **изменение ещё является кандидатом или уже считается новым текущим состоянием проекта?**

### Ветка, commit или pull request ещё не приняты

Используйте `CHANGE_REVIEW`.

```text
Используй architecture-code-review.
Сделай CHANGE_REVIEW принятого baseline против branch feature/payments.
Ничего не принимай автоматически.
```

`CHANGE_REVIEW` оценивает candidate в режиме только чтения. Он не закрывает существующие findings, не меняет Shared Technical Model, не продвигает Product baseline и не делает старые отчёты актуальными автоматически.

После завершённого пригодного Change Review принятие изменения выполняется отдельно через контекстный `RECONCILE_CHANGE` и существующих владельцев семантического состояния.

### Код уже принят как новое текущее состояние

Используйте `REVALIDATE`.

Skill должен определить затронутые зависимости и перепроверить только необходимый срез принятого состояния. Незатронутые доказательства и выводы переиспользуются.

### Изменилось только представление

Если исходная семантика не изменилась, а нужно исправить Markdown, Mermaid, навигацию или другое представление, используется `PROJECTION_REPAIR` либо явная регенерация соответствующей проекции. Представление не может исправлять семантический источник истины.

Полное руководство с таблицей решений и сценариями: [Что делать после изменения кода](docs/guides/after-code-changes.md).

## Основные сценарии работы

| Ситуация | Используйте | Что происходит |
|---|---|---|
| Аудита ещё нет | `NEW` | Создаётся новый пакет и подтверждается требуемая работа. |
| Незавершённая работа продолжается на том же baseline | `RESUME` | Продолжается существующая работа без нового аудита. |
| Нужно оценить ветку, commit или PR до принятия | `CHANGE_REVIEW` | Создаётся read-only оценка candidate. |
| Код уже принят как новый текущий source | `REVALIDATE` | Перепроверяется затронутое принятое состояние. |
| Нужно принять ранее проверенный candidate | контекстный `RECONCILE_CHANGE` | Candidate evidence направляется существующим владельцам для принятия решений. |
| Нужен дополнительный модуль или итоговый документ | `EXTEND` | Добавляется новая работа, существующие принятые результаты сохраняются. |
| Нужен уже принятый результат | `USE_EXISTING` | Новая техническая работа не запускается. |
| Сломалось только представление | `PROJECTION_REPAIR` | Исправляется представление без изменения семантической истины. |

Точные условия: [Справочник процессов](docs/reference/workflows.md).

## Текущие findings и история — не одно и то же

Пакет сохраняет историю findings, но исторический счётчик не используется как показатель текущего риска.

Пример:

```text
когда-либо зарегистрировано: 100
закрыто:                  40
найдено новых:            10
текущих:                  70
```

История выросла до 110 идентичностей, но текущий риск снизился до 70. Закрытые и замещённые записи не удаляются: они остаются в истории и сохраняют происхождение.

Принятый риск также не равен закрытой проблеме. Finding с принятой disposition остаётся технически существующим и показывается отдельно как остаточный принятый риск.

Подробно: [Жизненный цикл и актуальность](docs/concepts/lifecycle-and-freshness.md).

## Где лежат результаты

Skill хранит не только итоговые Markdown-отчёты. Типичный пакет содержит несколько классов состояния:

```text
working/INDEX.md
    состояние координации и маршрутизация

WS-* / EV-*
    исследовательские области и доказательства

Shared Technical Model
    принятые технические факты COMP-*, IF-*, INT-*, DS-*, EVENT-*,
    FLOW-*, AUTH-*, CFG-*, ERR-*

Architecture Review
    RF-* и связанные архитектурные артефакты

Test Engineering
    BC-*, CC-*, MAT-*, TM-*, GAP-*, TASK-* и связанные результаты

Code Quality Review
    CQ-* и связанные действия/представления

PRJ-*
    производные человекочитаемые проекции
```

`working/INDEX.md` — источник истины для координации процесса, но не для технических фактов или findings. Итоговый Markdown удобен для чтения, но не заменяет семантический источник истины.

Подробно: [Структура пакета аудита](docs/guides/audit-package-structure.md) и [Справочник артефактов](docs/reference/artifacts.md).

## Product и несколько репозиториев

Большой продукт может состоять из нескольких самостоятельных Project и репозиториев. Обычный каталог, в котором они лежат рядом, сам по себе не становится Product и не создаёт членство автоматически.

```text
/projects/
├── backend/
├── frontend/
├── gateway/
└── shared/
```

Skill может:

- обнаружить дочерние репозитории;
- найти существующие локальные аудиты;
- квалифицировать пригодные результаты;
- обновить только необходимые дочерние аудиты;
- собрать точный Product baseline;
- выполнить только недостающий межпроектный анализ.

Обновление дочернего аудита не продвигает Product baseline автоматически. Product переиспользует принятые child authorities, но не становится владельцем их findings.

Подробно: [Повторное использование и изменения](docs/guides/reuse-and-change.md).

## Что skill принципиально не делает

Чтобы не получать ложное ощущение уверенности, важно помнить несколько ограничений.

Skill:

- не считает итоговый отчёт семантическим источником истины;
- не считает найденный или сгенерированный тест доказательством `TESTED` без фактического исполнения;
- не принимает candidate Change Review автоматически;
- не продвигает baseline только потому, что branch был merged;
- не считает `WONT_FIX` или принятый риск автоматически `RESOLVED`;
- не удаляет исторические findings ради красивого счётчика;
- не запускает полный аудит после каждого commit, если достаточно адресной повторной проверки;
- не превращает Product в владельца child findings;
- не объявляет полный API только потому, что найдены некоторые endpoints;
- не выдумывает неизвестные значения, лимиты или контракты ради полноты документа.

## Обновление самого skill

Обновление `architecture-code-review` и изменение анализируемого проекта — разные процессы.

Чтобы обновить установленный skill:

```bash
cd ~/.agents/skills/architecture-code-review
git fetch origin --prune
git switch main
git pull --ff-only
```

После обновления начните новый сеанс агента.

Обновление самого skill не делает старый пакет аудита автоматически актуальным и не меняет baseline анализируемого проекта.

Подробно: [Обновление самого skill и откат](docs/operations/upgrade-and-rollback.md).
