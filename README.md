# Architecture Code Review

`architecture-code-review` — инструмент для глубокого инженерного анализа
существующих программных систем. Он помогает не просто собрать список
замечаний, а восстановить проверяемую картину системы, связать выводы с
доказательствами и сохранить результаты для продолжения, повторной проверки и
расширения после изменений проекта.

Главный принцип:

> **Ширина утверждения не должна превышать ширину доказательств.**

## Для кого

Инструмент рассчитан на:

- архитекторов и технических лидов;
- ведущих инженеров;
- команды сопровождения устаревших систем;
- инженеров по тестированию;
- команды, готовящие модернизацию, миграцию или крупную переработку;
- независимый технический аудит перед релизом, интеграцией или передачей системы.

## Какие задачи решает

`Review Suite` объединяет три независимых модуля проверки.

### Architecture Review

Восстанавливает фактическую архитектуру системы, проверяет владение состоянием
и ресурсами, жизненный цикл, границы компонентов и доверия, конкурентное
выполнение, обработку отказов и восстановление, а также подтверждённые
архитектурные корневые проблемы.

При необходимости дополнительно формирует `Target Architecture` и
`Remediation Roadmap`.

### Test Engineering

Проверяет, какие существенные поведения действительно доказаны исполняемыми тестами, где остаются пробелы в доказательствах, согласованы ли разные представления контрактов и какие Test Plan, Test Environment, Service Simulator или E2E Test Plan нужны. Для API может формировать конкретные негативные и граничные тестовые случаи по известным ограничениям. Сгенерированный или принятый тестовый случай сам по себе не означает `TESTED`: для этого нужны принятые доказательства фактического исполнения.

### Code Quality Review

Находит не просто стилистические замечания, а конкретные механизмы реализации с
доказуемым существенным последствием для сопровождаемости, надёжности,
тестируемости, жизненного цикла ресурсов, конкурентности, зависимостей,
локализации и других качеств. В том числе проверяет устойчивость API к входным данным: лимиты тела запроса, строк, коллекций и загрузок, порядок валидации и ситуации, когда большой запрос успевает быть прочитан или материализован до отклонения на уровне схемы.

Модули можно использовать отдельно или вместе. Ни один из них не является обязательным родителем другого.

## Что вы получаете

В зависимости от выбранной конфигурации инструмент может сформировать:

- Architecture Review;
- Authoritative Findings Ledger;
- Target Architecture;
- Remediation Roadmap;
- Test Assurance;
- Test Plan;
- Contract Consistency Report;
- Test Environment Design;
- Service Simulator Design;
- Service Simulator Implementation Plan;
- E2E Test Plan;
- Code Quality Findings View;
- Code Quality Summary;
- Maintainability Hotspots;
- Code Quality Roadmap Contribution.

Кроме итоговых документов инструмент сохраняет доказательства, фактическую техническую модель, записи соответствующих модулей и состояние процесса. Поэтому повторная проверка не зависит от памяти конкретного чата или агента.

## Установка

Для Codex, OpenCode и других агентов, использующих `~/.agents/skills`:

```bash
git clone \
  https://github.com/todkavodka/architecture-code-review.git \
  ~/.agents/skills/architecture-code-review
```

После установки начните новый сеанс агента.

Проверить установленную ревизию:

```bash
git -C ~/.agents/skills/architecture-code-review rev-parse HEAD
```

Подробно: [Установка, обновление и проверка](docs/getting-started/installation.md).

## Быстрый старт

Самый простой запрос:

```text
Используй architecture-code-review для этого проекта.
```

Инструмент сначала определит репозиторий, базовую ревизию и существующие пакеты
аудита, затем предложит подходящий сценарий работы (`Session Intent`).

Для нового аудита показывается Review Suite:

```text
[ ] Architecture Review
[ ] Test Engineering
[ ] Code Quality Review
```

Эти три пункта остаются семантическими модулями проверки, но для `NEW` теперь важен не сам факт выбора модуля, а непустой `Requested Work`. Допустимы три формы запроса:

```text
capability-only
standalone-output-only
mixed
```

То есть можно выбрать один или несколько модулей, либо запросить допустимый самостоятельный итоговый документ/представление без искусственного включения модуля. Пустой `Requested Work` недопустим. Один только контекст `Product` тоже не считается работой.

Для Architecture Review отдельно выбираются глубина исследования и конечный
результат:

```text
Depth:
  STANDARD_FULL
  FORENSIC

Endpoint:
  REVIEW_ONLY
  REVIEW_PLUS_TARGET_ARCHITECTURE
  REVIEW_PLUS_TARGET_AND_ROADMAP
```

Глубина и конечный результат независимы: любой из двух вариантов глубины поддерживает любой из трёх конечных результатов.

Выбор модуля открывает его отдельную конфигурацию. Для Test Engineering
Test Assurance является обязательным, а остальные результаты явно выбираются
или явно отмечаются как не выбранные. Для Code Quality Review так же отдельно
разрешается каждый из четырёх человекочитаемых результатов; отсутствие выбора
не является подтверждённым отказом. Перед началом работы инструмент показывает
единое резюме Requested Work и ждёт подтверждения. Standalone output/view и
результаты, принадлежащие выбранному модулю, остаются разными частями выбора.

После конфигурации выбранных модулей в NEW всегда показывается отдельный
раздел Standalone Outputs / Technical Documentation. Можно выбрать Provided
Interfaces, Consumed Interfaces, Integrations, Auth and Trust, Failure Behavior
и другие применимые зарегистрированные представления либо явно подтвердить
NONE. Это не четвёртый модуль. Запрос API Report предлагает ограниченный набор
интерфейсов и интеграций для подтверждения; он не создаёт новый тип отчёта.
Все три модуля сами по себе не включают эти представления.

Подробные `Provided Interfaces` и `Consumed Interfaces` показывают отдельные
учтённые операции в пределах выбранного среза и сохраняют evidence и
ограничения. `PARTIAL`, `UNKNOWN` и `UNRESOLVED` остаются видимыми;
неизвестная схема операции не превращается в выдуманную деталь. Формулировки
«полный API», «все endpoints» и эквивалентные им допустимы только при принятом
`OPERATION_INVENTORY_COMPLETE` для точно выбранного подробного среза и
действительном снимке зависимостей. Одного статуса `CURRENT` для этого
недостаточно.

`STANDARD_FULL` и `FORENSIC` у `Architecture Review` относятся к покрытию
материальной архитектурной поверхности и не обещают перечисление каждого
endpoint. `EXTEND` может адресно запросить углубление operation inventory для
выбранного Project, baseline, направления, протокола и среза; несвязанные
области не пересобираются. Обычный запрос остаётся однопроектным. В режиме
`Product` операции агрегируются только с точной квалификацией участника,
ревизии и baseline: одинаковый method/path у разных участников не становится
одной операцией, а недоступность или расхождение участника показывается как
ограничение.

## Change Review: что изменилось между двумя состояниями

Когда нужно проверить ветку, commit или pull request относительно принятого
baseline, явно запросите `CHANGE_REVIEW`. Инструмент сравнивает выбранные
`BASE` и `CANDIDATE` и показывает кандидатные факты, находки и влияние только
как review-контекст. Принятые факты, находки, тесты, совместимость и проекции
не изменяются автоматически.

После завершённого и пригодного Change Review пользователь может отдельно
подтвердить контекстное `RECONCILE_CHANGE`. Оно направляет изменения к
существующим владельцам; только после их решений можно продвинуть baseline.
`RESUME` и `EXTEND` останавливаются при несовпадении source baseline,
`PROJECTION_REPAIR` не чинит проекцию для изменённого источника, а
`REVALIDATE` заново оценивает затронутое принятое состояние.

Результаты для эквивалентного merge можно переиспользовать только при
сохранённом доказательстве равенства всего дерева или точно зафиксированного
релевантного среза. После принятого изменения влияние на проекции учитывается
отдельно; генерация `RG-*` остаётся явным действием пользователя. В Product
режиме каждый участник сохраняет собственную ревизию и baseline.

## Примеры

### Архитектурный аудит

```text
Используй architecture-code-review.
Нужен новый Architecture Review: STANDARD_FULL, REVIEW_ONLY.
Test Engineering и Code Quality Review не включай.
```

### Анализ качества тестов

```text
Используй architecture-code-review.
Нужен Test Engineering: Test Assurance + Test Plan.
Architecture Review и Code Quality Review не включай.
```

### Анализ качества реализации

```text
Используй architecture-code-review.
Нужен Code Quality Review: Findings View + Summary.
Architecture Review и Test Engineering не включай.
```

### Проверка API на граничные входные данные

```text
Используй architecture-code-review.
Проверь API на отсутствие лимитов входа, oversized body, строки и коллекции,
порядок валидации и подготовь негативные граничные тестовые случаи.
```

Например, наличие `maxLength: 255` у поля не доказывает защиту от запроса с гигантским телом, если сервер сначала целиком читает тело в память. Инструмент рассматривает транспортный лимит и ограничение поля как разные границы и не объявляет безопасность без доказательств реального места применения ограничения.

### Повторная проверка после изменений

```text
Используй существующий пакет аудита и REVALIDATE изменения после предыдущей принятой ревизии.
```

Полные сквозные сценарии: [Сквозные примеры](docs/index.md#сквозные-примеры).

## Повторное использование результатов

Review Suite рассчитан на длительную жизнь пакета аудита:

| Ситуация | Используйте |
|---|---|
| Начать новый аудит | `NEW` |
| Продолжить незавершённый | `RESUME` |
| Проверить изменения проекта | `REVALIDATE` |
| Добавить модуль, итоговый документ или конечный результат Architecture Review | `EXTEND` |
| Использовать уже принятый результат | `USE_EXISTING` |
| Исправить только Markdown, Mermaid, ссылки или формулировки | `PROJECTION_REPAIR` |

Изменившийся Git HEAD сам по себе не означает, что весь аудит нужно выполнять
заново. `REVALIDATE` проверяет затронутую область по зависимостям и сохраняет
принятое состояние, не затронутое изменениями. Полные правила сценариев работы
приведены в [справочнике процессов](docs/reference/workflows.md); различие между
повторной проверкой и пересборкой документов — в разделе [о жизненном цикле и
актуальности](docs/concepts/lifecycle-and-freshness.md).

## Важные свойства

- Доказательства и технические факты привязаны к конкретной базовой ревизии.
- Человекочитаемый отчёт не становится источником истины только потому, что он существует.
- Семантическое состояние и актуальность итоговых документов отслеживаются отдельно.
- Новый итоговый документ можно добавить через `EXTEND`, не повторяя не связанные с ним уже принятые этапы.
- Исправление оформления не имеет права менять принятое техническое содержание.
- Старые пакеты согласуются консервативно; предыдущие результаты не переписываются молча.
